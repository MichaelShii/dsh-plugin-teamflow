# TeamFlow 执行路径基准（需求清晰度 × 质量门禁：assetd 资产分组）

> 同一需求、同一基线、两种执行路径的横向测量。**与 [`hold-pipeline-vs-native.md`](./hold-pipeline-vs-native.md) 配对**——
> 那篇是「小需求 + 需求书边界未写全」，本篇是「中需求 + 需求书把边界写死」，
> 两篇合起来构成**「需求书歧义存量 → 质量门禁收益」**这一维度的两个数据点。
>
> ⚠️ **本篇的主指标是平局（负面结果，对 TeamFlow 不利）**。它的用途**不是**证明流水线质量更好，
> 而是**标定流水线质量优势消失的条件** —— 这是本次最有信息量的产出。

## 关键发现

### 1. 平局的根因：需求书把陷阱全写死了 → 考执行力而非设计力

- 盲测集的 23 条**全部在 `REQUIREMENT.md` 里有明确依据**——这是合法盲测的**必要条件**
  （测需求书没写的东西 = 猜谜，会误杀合法实现）。
- 而 `REQUIREMENT.md` 把这需求的所有陷阱**都点破了**：「v1/v2 必须直达 v4」「迁移幂等」
  「`(ungrouped)` 即使 0 也要在」「`-` 是保留字」「改名不动归属、删组不删资产」「CLI 与 lib 必须一致」。
- 于是本次测的不是「**有没有想到没写的**」，而是「**有没有老实执行写了的**」——**两个 agent 都老实执行了。**

这是一处**基准设计两难**，本次恰好选了错的一侧：

| 需求书写法 | 盲测合法性 | 区分度 |
|---|---|---|
| 只给目标，边界处理留白 | 边界点必须在需求书有依据 → **写全才合法** | 边界可从目标唯一推导 → **有区分度（考设计力）** |
| **把陷阱全部点破（本次）** | 合法 | **无区分度（考执行力，两边都会）** |

assetd 这次把「旧格式兼容 / 引用完整性 / 幂等」这些**流水线本要防的病**直接写进了需求书，反而**替两条路径都排掉了雷**。

### 2. ⭐ 与 hold 篇配对后的规律：门禁价值随需求书歧义存量递减

| | `hold-pipeline-vs-native`（小需求） | 本篇（中需求） |
|---|---|---|
| 需求书边界 | 只列 AC 编号，**未写全** | **点破版**（陷阱全写死） |
| 质量 | **A 更强**（原生漏 AC-16/17 独立音效，且测试零覆盖照样提交） | **平局 23:23** |
| 代价 | A 贵 **44%** | A 贵 **262%**（3.62× token）／**69%**（1.69× 时间） |
| 平局/差异的成因 | 原生**没有** AC 逐条核对机制与 QA 门禁 | 需求书**替两条路径都排掉了雷** |

⇒ **初步规律（待检验）**：**流水线质量门禁的边际价值 ≈ 需求书的歧义存量。**
需求书把验收边界写全时，门禁的增量价值 → 0，只剩成本；需求书留白时，门禁是唯一能兜住「静默漏项」的机制。
**n = 1 / 臂 × 2 个点，只能算倾向，不能算结论**——但它是目前唯一能把两篇基准串起来的一条线，
也直接给出了下一版基准的难度来源（见「优化方向」末条）。

**注**：两篇的「质量」判定方式并不同级 —— hold 篇是**同一套脚本两边跑**（判定与实现耦合：
「A 更强」实质是「原生没写专项测试」）；本篇是**对两臂独立的盲测**（26 可见 + 23 盲测，两臂都看不到）。
**本篇的质量结论证据级别更高。**

### 3. 「改需求书」的天花板已被量化：12 / 23

对 23 条盲测点做了**信息来自哪里**的分级（详见工作台 `v2/ANALYSIS-heldout-provenance.md`）：

| 类别 | 条数 | 含义 |
|---|---|---|
| (a) 已被可见用例 `visible.json` **直接示范** | **8** | H04 H06 H11 H12 H14 H15 H16 H22 —— **改需求书零收益**（H11 被 V11 一字不差示范、H22 被 V22、H06 被 V18） |
| (b) 未示范但**可从目标唯一推导** | **12** | H01 H02 H05 H07 H08 H09 H10 H13 H18 H20 H21 H23 —— **这才是改需求书的收益面** |
| (c) 未示范且**不可推导**（歧义 / 接口合同） | **3** | H03 H17 H19 —— **必须明写**，删了会误杀合法实现 |

⇒ **只改 `REQUIREMENT.md` 的区分度天花板 = 12/23 ≈ 52%**；要突破必须**同时**降低可见用例的
「陷阱示范密度」。**光把需求书写虚是不够的** —— 这是下一版基准最容易踩的坑。

(c) 类三处**必须保留**（靠读 base 实现体确认，非推理）：① `(ungrouped)` 空桶恒存在
（`src/stats.mjs` 的 `bump()` 是**惰性建桶**，沿用既有模式者会自然省略空桶 → 与期望相反）；
② `set` 也支持 `--group`（**接口选择**，不可推导）；③ `-` 是保留字（两种消解都说得通 → 歧义）。

### 4. 方法论：**从 journal 扣掉可归因的 bug 开销**，不必等重跑

A 首跑墙钟 45.2 min 里有 **16 分 03 秒**是产品 bug 造成的死时间（假熔断停线 → 人工 resume）。
当时按 journal 逐笔剥离（只把 `seq=7` 假熔断尝试与 `seq=14` 补跑 T5 算作可归因附加项），
推出 token **3.44–3.57×**、时间 **1.98×**；次日 A' 复跑实测 **3.62× / 1.69×** —— **推算被验证**。

⇒ **「基准跑在带 bug 的版本上」不必作废重跑**：先按时间线逐笔剥离可归因开销、给区间，
再用一次单变量复跑交叉验证。这个方法可复用。

### 5. 基准反过来改产品：一次实验钉出 **4 处真实缺陷**

| # | 缺陷 | 证据锚点 | 修复 |
|---|---|---|---|
| 一 | `judgeDeliverable` 把**如实汇报**「沙箱里跑不了测试」当成拒绝 → 判 `insubstantial`（视为未交付） | `seq=7` `outcome=insubstantial`，而该子代理 `stopReason=completed`、证据块/state 块齐全、代码已落盘 | `affdc21` 三级判据（客观形态 → 真交付信号 → 措辞兜底） |
| 二 | 熔断预算误计 `cacheRead` → 报「累计 1886k 超预算 60k」，**真实新增仅 55,439** | `seq=7` usage `34,799+1,830,144+0+20,640` = **1,885,583** / fresh **55,439**（与修复提交 before/after 逐位一致） | `affdc21` 熔断改 `freshTokensOf`（排除 `cacheRead`），`FRESH_TOKEN_BUDGET=200k` |
| 三 | 裸 `git add -A` 收口，把 prompt 明确定义为「非交付物」的 **208 个自有日志（92%）** 扫进提交 | 提交里确有那 208 个文件；子代理报告当时已写「logs/ remain untracked」**属实** ⇒ **契约在 host 侧破** | `affdc21`：`tfAddArgs()` pathspec `:(exclude)logs/teamflow` + `mergeGitignore()` 幂等补写，配 `test/gitignore.test.js` |
| 四 | prompt 里日志布局写成**未限定的相对昵称** `scripts/`、`probe/` → 模型解析成**项目根**，6 个一次性草稿被提交 | A' 的提交 `e5e8a53` 里：runId 目录下 13 个同类脚本全被排除，**仓库根 `scripts/`(5) + `probe/`(1) 进了提交** | `1a4de5a`：四条路径全部改写为完整限定 `logs/teamflow/<runId>/...` + 段首加粗禁令 + dev/qa/qaFix 三处重申 + L1 契约 `LOG-LAYOUT-SCOPED`（含防回退断言） |

**四处的处置结果（A' 复跑实测）**：停线 **16 分 03 秒 → 0**；`熔断` / `insubstantial` /
`需人工介入` / `提测门禁` 计数 **各 ≥1 → 全 0**；阶段 **18 段（含 resume 补跑 + QA 打回）→ 8 段连续，QA 零返工**；
`logs/teamflow` 噪音 **208 个 → 0 个**（`.gitignore` 被幂等补入）。

**教训（沉淀为纪律）**：**给模型指路径必须给「完整限定路径」，不能给「通用昵称」** ——
`scripts/`、`probe/` 这类项目常用目录名会被按最宽松、最像「项目约定」的方式解析。
与「措辞不能当交付判据」同源：**歧义表述总是被往宽松处解释**。

## 优化方向复核（对照 hold 篇的判定，不重复投入）

hold 篇已判定为**假优化**的项（共享已读文件全文 / 拆任务存在性预检 / 强制削减护栏 / 测试任务合并），
本篇**未发现任何推翻该判定的证据**，**不再重复投入**（见 `AGENTS.md` 优化禁令）。

本篇新增的、**已落地**的一项：

1. **产物边界 = 允许清单语义（部分落地）**：`affdc21` 已加两道防线（pathspec 排除 + `.gitignore` 幂等补写），
   `1a4de5a` 已修 prompt 作用域。**残留**：pathspec 与 `.gitignore` 仍只覆盖 `logs/teamflow/` 一个前缀 ——
   **是「点名黑名单」而非「划一条边界」**。若未来出现第三个临时产物目录仍会漏。
   独立建议（**与本轮泄漏无因果，仅作改进项**）：排除列表可配置多前缀，或收口改**允许清单**。

**下一版基准的难度来源（推导自关键发现 2 与 3）**：

2. **需求书只给目标与不变式，边界处理留给推导**；同时**降低可见用例的陷阱示范密度**
   （建议 V10/V11/V07/V20/V23 改写为只测接口形状，行为移入 held-out）。
   两支柱缺一不可：只改需求书 → 天花板 12/23；不改可见用例 → 另 8 条继续被示范。
3. **每条盲测点补「推导链」**（为什么这是唯一正确读法），否则作者兼 TeamFlow 作者的双重身份
   会让「合法盲测」这一点站不住。
4. **加大规模与耦合**，让「单会话整读」真正开始吃亏（这是流水线要防的病本身）。
5. **统一两臂的采集口径**（本次 A 用宿主投影、B 用界面自报，不可直接相减）。
6. **两侧沙箱权限锁死为同一档并记录在案**（本次 A 受限、B 放宽，是未受控变量）。
7. **n ≥ 3 / 臂**，否则只能当轶事。

## 结论

- **在「需求书把验收边界写全」的中等需求上，两条路径质量完全相同（盲测 23:23、零假交付）**，
  而流水线多花 **≈3.6× token / ≈1.7× 时间**（去污染口径）。
- **这不是「流水线没用」**：它的质量门禁价值在这一侧被**关掉了**——需求书替两条路径都排掉了雷。
  与 hold 篇（需求书留白、原生漏 AC）并置，才构成完整图像：**门禁的边际价值 ≈ 需求书的歧义存量。**
- **本次 A/B 最有价值的产出不是「谁更好」，而是 4 处被钉出来的真实缺陷**（三个由首跑驱动为 `affdc21`、
  一个由 A' 驱动为 `1a4de5a`），以及**一条被实测验证的去污染方法论**。
- **「A 自主跑完」在首跑不成立**（需一次人工 `teamflow_resume`）；**A' 复跑已证伪该缺陷**（零停线、零熔断、QA 零返工）。
- 对外可用口径：**v0.1.8 @ `900d6c7`（首跑）/ `2aa63b5`（A' 复跑）**；「227 files」「3.87× / 3.07×」
  均为**修复前实测值，不得当作当前版本行为**（修复后预期 ≈19 files、≈3.6× / ≈1.7×）。

## 局限与变量

- **⚠️ 作者双重身份（最大方法学弱点）**：基底、需求书、两套用例、参考实现**全部由 TeamFlow 作者手写并自审**。
  **需求书的清晰度是作者的自由变量** ⇒ 「平局」很可能是「作者把需求书写得太清楚」的产物。
  关键发现 3 的分级表正是**对这一弱点的自证**，但它不能消除偏差，只能界定范围。
  参考实现是「照着自己写的需求写实现」，**不是独立第三方复核**。
- **⚠️ n = 1 / 臂**（A' 是第二次 A，但同属一臂、且含另一处变量），是轶事不是数字。**要写进 README 需 n ≥ 3 / 臂。**
- **⚠️ 两侧沙箱权限可能不对等**：A 的子代理在受限沙箱里撞上「禁止 Node 捕获子进程管道」（`spawnSync` EPERM）
  并**自建 shim 绕行**（`spawn-inprocess.cjs` 等）；B 则是**报告限制、请作者放宽权限后在放宽条件下完成验证**。
  ⇒ 严格说 **B 是在更宽松的权限下测出的**（对 B 有利）；且该障碍是**两条路径共同撞上**的。
- **⚠️ 两臂 token 口径不同**：A 是宿主官方投影（可逐阶段累加验证）；B 是**应用状态栏自报**
  （三桶相加与标注总数吻合、命中率吻合，内部自洽，但无法逐阶段核验，也不能排除只统计了部分轮次）。
  **引用 B 的数字必须注明来源。**
- **⚠️ 任务粒度混淆**：A' 的技术蓝图把 dev 拆成 **4 个任务**，首跑拆成 **11 个** —— 这是模型在 tech 阶段的
  不同次生成，**与修复无关**。佐证：总 token 只降 6%，但调用数降 37%、墙钟降 45%。
  ⇒ **「修复让代价降了 45%」是错的**，正确说法是「两个因素无法分离」。
- **⚠️ 版本口径**：A 首跑跑在「收口提交修复前」的部署副本上（`900d6c7`）；
  A' 跑在 **`2aa63b5`**（= `affdc21` + 补 17），**不是** `affdc21`。
- **⚠️ 记录保真问题**：journal 的 `humanIntervention` / `cancelled` / `interrupted` 字段在首跑**全为 `false` 却未置位**
  （实际发生过人工 resume）⇒ **该字段当前不可用于判断有无人工介入**，需同时检查停线/resume 事件与时间戳空洞。
  **本次未验证、仍未修。**
- **A 的「full 档」实际只跑 5 个阶段**（`needDesign=false` / `needScaffold=false` / `productRoot=null`）
  —— 对外说「full 档」**必须附这一条**，否则会被读成 7 段全跑。
- **两篇基准的「质量」判定方式不同级**（hold 篇判定与实现耦合；本篇为独立盲测），
  并列时**必须注明**，不能当成同一口径的两个样本。
- **任务形状是选择过的**：刻意选「加功能 + 旧格式兼容 + 跨模块」以放大差异（对流水线有利）；
  同时 0→1 小需求的固定开销占比最高（对流水线不利）。**两个方向都要写。**
- 0.1.7 起 TeamFlow 对机械阶段（scaffold / patch 单点确认）下发 `reasoningEffort: low`，
  原生路径走宿主默认 `high`。本次 full 档未含 scaffold，但 **dev 等阶段的 effort 差异仍可能存在**。
- 顺序执行、同一台机器，不做并行或资源竞争对照。
- **本机环境坑（影响可复现性）**：`git checkout feat/teamflow` → `feat/native` 时 git 会把
  **`tests/` 下 8 个「两分支内容相同」的文件从工作区删掉**（稳定复现，根因未定位，
  怀疑与 `core.autocrlf=true` + `.gitattributes` 的 `eol=lf` 在 Windows 上的重写路径有关）。
  git 对象完好，`git checkout -f HEAD -- .` 可完整恢复，**修复后两侧判分均重跑复现**。
  **强制动作：每次切分支后先 `git status --porcelain` 核对。**
