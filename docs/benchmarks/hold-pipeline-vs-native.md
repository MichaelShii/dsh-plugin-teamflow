# TeamFlow 执行路径基准（小需求样本：Hold 暂存方块，r14）

> 同一需求、同一基线、两种执行路径的横向测量（小需求样本，补全 v0.10.2 大需求基准的规模曲线）。
> 目的：量化「编排流水线」相对「让模型直接干」在**小需求**上的时间 / token / 调用 / 质量差异，并定位流程层面的差距点。

## 实验设置（2026-08-27）

| 项 | 值 |
|---|---|
| 需求 | Tetris「Hold 暂存方块 + 开关」（r14，AC-1~17：暂存/交换/每周期限 1 次/开关/持久化/预览/音效） |
| 产品基线 | `main`（`e3488d1`，v3.1 消行动画已合入，**未实现 Hold**） |
| 路径 A（流水线） | TeamFlow lite 档 + 软件开发团队，run `tf-mtb58jz9-deu2kl`，分支 `feat/hold-piece-toggle`（`dc0e01f`） |
| 路径 B（原生） | 原生 DSH 单会话，分支 `feat/hold-piece-toggle-main`（`147d745`），会话 `session-28eeb563` |
| 对照控制 | 同基线（e3488d1）、同需求；路径 B 独立分支、未读流水线产物；两分支均跑通七套验证脚本复核 |
| 度量口径 | 官方口径 billed = input + cacheRead + cacheWrite；流水线取 run journal，原生取 DSH 会话 usage（`inputTokens`/`cacheReadTokens` 聚合） |

## 结果对比

| 指标 | 路径 A（流水线） | 路径 B（原生 DSH） | 差异 |
|---|---|---|---|
| 总耗时 | ~47 分钟 | ~28 分钟 | **B 快 40%** |
| 模型调用次数 | 393（115 步×子代理 + 阶段） | 120 | **B 少 70%** |
| billed token | **17.48M**（input 0.68M + cacheRead 16.8M） | **9.69M**（input 0.14M + cacheRead 9.56M） | **B 省 44%** |
| 缓存命中率 | 96.1% | 98.6% | 相当（B 略高） |
| 真实思考+生成（output+input） | ~0.83M | ~0.16M | A 多 5 倍（多阶段多报告） |
| 交付产物 | 18 文件 +2155/-23（含任务夹 PRD/DESIGN/TECHNICAL/QA/ACCEPTANCE 5 文档） | 8 文件 +165/-5（纯代码） | 规模不同（含文档） |
| 质量（功能） | 七套全绿（410/410 含 35 项 Hold 专项） | 七套全绿（基线 268/268，**无 Hold 专项**） | 见下节 |
| 质量（AC 覆盖） | AC-1~17 全实现+逐条验收 | **AC-16/17（hold 独立音效）未实现**（复用 rotate） | **A 更强** |

## 关键发现

1. **小需求上流水线不再省 token，反而多花 44%**（大需求 v0.10.2 是省 39%）——规模拐点实证：
   - 流水线固定开销 = 6 个阶段 agent ×（读代码库 + 状态注入）+ 10 个子 agent ×（全套蓝图/PRD/状态注入）
   - 需求越小，固定开销占比越高，拆分收益（上下文隔离）覆盖不了启动成本
2. **17.48M 里 16.8M（96%）是缓存重放**，真实思考仅 0.83M（原生 0.16M）。token 大头不是「想」，是「同一份文件被 N 个 agent 各读一遍再重放」
3. **流水线的质量门禁价值在小需求上更凸显**：原生没有 QA/验收门禁，AC-16/17 音效缺失、测试零覆盖照样提交；流水线 QA 阶段逼出 470 行 Hold 专项测试 + 验收逐条核对
4. **「功能等价」不成立**：七套全绿两边都过，但原生的「全绿」是基线测试不覆盖 Hold（回归盲区）；只有流水线有 Hold 专项断言

## 流程差一点在哪里（本次对照定位）

> 不是「模型能力差」，是编排层可量化的流程差距点，按影响排序：

1. **子 agent 启动的固定注入开销 × 10（最大头）**
   - 每个 dev 子 agent 都注入全套 STATE_BLOCK（蓝图 825 行 TECHNICAL.md + PRD + 状态块 + 文件作用域）
   - 同一文件被重复整读：game.js 被 8 个子任务读（T1/T7/T10/QA…），verify-game.cjs 被 4 次——token 观测全程 17 条「重复 read」warn，但**只观测不削减**
   - 流水线 cacheRead 16.8M vs 原生 9.56M（+76%）正是这一项的差
2. **蓝图拆任务对「已存在目标」误判（T5 类）**
   - T5（index.html Hold DOM）拆成独立子 agent，实际「已验证无需改」（2 calls）——拆任务前无存在性预检
3. **测试任务 4 个（T7-T10）各自重读被测代码**
   - 每测试 agent 独立上下文：T7 读 game.js + verify-game.cjs 两遍起，T10 读 game/ui/persist/qa-e2e 全套
   - 测试工程与实现共享被测文件，上下文隔离在这里是负收益
4. **阶段门禁串行成本（lite 档）**
   - PRD→design→tech→dev→QA→验收 6 个阶段 agent 各读一遍代码库（PRD/QA 已用 head+tail 切片压缩，dev 子 agent 仍是重头）
5. **「观测→执行」断链**
   - token 观测护栏（重复 read/验证脚本循环）全部只 warn 不拦截——本次 17 条 warn 零削减动作，护栏是仪表盘不是刹车
6. **原生侧缺失项（流程反面）**
   - 原生无 AC 逐条核对机制 → 音效 AC 静默漏实现；无 QA 门禁 → 测试零新增也提交。**这是原生「省」的来源之一，也是不可模仿的部分**（省的是质量预算）

## 优化方向复核（2026-08-27 二评：修正初版结论）

> 初版把「16.8M 缓存重放」当成主战场并提议共享已读文件——复核后判定**方向反了**，逐条修正：

| 初版提议 | 复核判定 | 理由 |
|---|---|---|
| a. 子 agent 共享「已读文件全文」 | ❌ **假优化** | 注入=prompt 前缀、每次调用全价重放；而自读走 cacheRead（命中价 ≈ 未命中 **1/10**），重读更便宜；全文注入还污染上下文隔离（TOKEN_HYGIENE 价值反噬） |
| a'. 共享「读后结论」（契约级） | ✅ 真优化但**已有机制** | `<!-- state -->` 块的设计意图（≤500 字摘要）；实际粒度粗、模型产出不可靠——加强是增量 |
| b. 拆任务前存在性预检 | ❌ 假优化 | T5 浪费 ≈ 41k billed ≈ 总消耗 **0.2%**；预检成本 > 收益 |
| c. 测试任务合并（T7-T10 → 1-2 个） | ❌ **假优化（复核改判）** | 合并 = 单 agent 上下文累积（4 被测文件 + 4 脚本每轮重放）：估算 cacheRead 18.8M vs 分开 7.9M——**分开便宜 58%**，上下文隔离原则反向实证 |
| d. 护栏升级为强制削减 | ❌ 假优化 | 「强制」= 替模型决策；重复 read 常是写断言的合理需求，砍了伤质量 |

**关键洞察（修正认知的三条）**：
1. **billed 口径 ≠ 成本**：cacheRead 命中价 ≈ input 的 1/10，16.8M cacheRead 的真实成本 ≈ 1.7M 等价（按价格：流水线 ~2.5M vs 原生 ~1.1M，差距从账面 7.8M 缩到 1.4M）
2. **重放成本 = 上下文长度 × 调用次数**（T7：34 轮 × 43k/轮）——真正该砍的是「每子 agent 的注入前缀」与「调用轮次」，不是「read 次数」
3. **流水线多花的 44% 是质量预算，不是浪费**：470 行测试 / AC 逐条验收 / 全套文档是排他性产出，原生花不出的钱；优化方向是「让质量更便宜」，不是「去掉质量」

**真优化清单（复核后收敛——只剩一项已落地，其余判定不投入）**：
1. **护栏「观测→执行」闭环（已实施 2026-08-27）**：token 观测第 3 次重复 read / 脚本重复执行时，除 journal warn 外同步 `run.inject` 轻提醒（不打断，下一轮 step 可见）——从「只观测」升级为「观测+引导」；修的是「17 条 warn 零削减」的观测失效缺陷，非凑数优化
2. **tech 分层注入（判定不做）**：billed 省 ~2M 但真实成本仅 ~0.3M 等价（首轮 input 全价、后续 cacheRead 1/10 价；每轮重放中已读文件 30k+ 才是大头，注入仅 ~10k，切了只省 1/4）；风险 = dev 失去散文「为什么」→ QA 打回（v0.10.2 教训）+ 自由文本切段脆弱 + grep 逃生通道部分抵消收益；实证 run tf-mtb58jz9 在「蓝图 JSON + 全文注入」下 10 任务零打回。触发条件：tech 产出 >15k token 时重新评估
3. 环境限制预置（QA 每次论证人工补测清单）：收益 ~1.5min/run，暂不做（鸡肋）

## 结论

- **小需求（<300 行改动）：原生更优**（快 40%、省 44%），但必须接受「无专项测试、AC 可能有漏」的质量缺口——适合一次性/探索性需求
- **流水线适合「需要验收级质量 + 文档资产」的需求**：多花 44% token 买的是 470 行测试 + AC 逐条核对 + 全套文档；且该 44% 按真实价格口径缩水为 ~1.4M 等价，「质量预算」属性更强
- **token 优化的主战场是「注入前缀 × 调用轮次」**（devPrompt 全文注入 → 按任务切片；测试任务合并），**不是缓存重放本身**——cacheRead 是便宜的，16.8M 账面数字会误导优化方向
- **大需求仍以 v0.10.2 结论为准**（流水线省 39%）；规模拐点约在「一次性改动量」与「固定开销 10-15M」交会处，需更多样本精确定位

## 局限与变量

- 单次测量，LLM 有随机性；严格结论需多轮取均值
- 路径 B 会话含「先读 AGENTS.md/文档再动手」的探索开销，与流水线 dev 子 agent 的「已注入」不等价——但这是原生真实工作流的一部分
- 两分支模型配置同为 DSH 默认（`mimo-v2.5`），无模型变量
- 流水线 billed 含 QA/验收/PRD/design 阶段的非实现 token，原生无对应物——「省 44%」部分来自砍掉这些阶段本身
