## 0. 结论速览（先给答案，细节见后）

实验于 2026-10-01 全部跑完：**A 组 = craft 开**、**B 组 = craft 关**（同模型 hy3）、
**C 组 = dsh 原生单会话（完全不走流水线）**。三组产物均**冻结留存、未做任何修补**。

### 0.1 一句话结论

**在这个样本上，craft 条款没有产生净收益；而流水线的固定开销远大于条款自身的边际成本。
但该修的不是条款，是「下游没人判产物自洽」——条款的作用面与成本量级都已经被量出来了。**

### 0.5 处置建议（均已落地，见下方状态）

**① 条款收窄 —— 已落地（2026-10-01）**

- `2b`（design 视觉规格）新增两条子项：
  - **几何自洽**：组件把文字放进有边界的形状里（圆环 + MM:SS、徽标 + 文案、HUD 槽位 + 数值）时，数字必须真的装得下 ——
    按**尺寸函数能取到的最大值**算（例如 clamp 的上限），不是按平均值；`r − stroke-width` 必须大于文字外接半对角。
    自己两个小节打架时，改到自洽并把最终数值写下来。
  - **定位收窄**：这一节是「交互反馈与状态可见性的下限」（hover / focus / pressed / disabled / 全状态下常驻信息可见），
    **不是审美裁决** —— 按 AC 与上面这些数字判，不按品味判。
- `4b`（dev craft bar）新增一条：装得下文字再装数字 —— 若 DESIGN.md 的容器值与内部文字在解析尺寸下装不下，
    **保留数值、让内容自适应，并在 summary 里写明这个冲突**；绝不交付数字压环/裁切的布局。
- 状态：见 `host/prompts/index.ts`；`test/craft-link.check.mjs` 改后仍全绿（design prompt 开 7874 / 关 5419 字符，差 31.2%）。

**② 产物自洽探针 `scripts/artifact-selfcheck.mjs` —— 已落地**

三条判据全是**静态解析、host 可判、模型无关**（不假设任何模型能力，不需要浏览器）：

| 判据 | 判什么 | 静态怎么判 |
|---|---|---|
| `[geo]` 几何自洽 | 数字压环 / 压线 | `circle 的 r − stroke-width` vs 居中文字外接半对角（字号取 clamp 上限） |
| `[bind]` 未绑定按钮 | 点了没反应 | `<button>` 的 id / class / `data-*` 在产物 JS 里一次都没出现 |
| `[bind]` 歧义选择器 | 只有第一个元素活着 | `querySelector('[x]')` 而 DOM 里该属性出现 >1 次 |

用法 `node scripts/artifact-selfcheck.mjs <产物目录> [...]`（退出码 0/1，可多目录批量）。
**首跑实证（直接喂冻结的 r1 / r2 / r3）**：

| 产物 | `[geo]` | `[bind]` | 存储 |
|---|---|---|---|
| r1（A） | ❌ 余量 **−27.5px**（半对角 141.5 > 可用半径 114） | ❌ `querySelector('[data-close]')` 命中 2 个元素 ⇒ 「好的」是死按钮 | 有 |
| r2（B） | ✅ +38.4 / +75.1 | ✅ | 有 |
| r3（C） | ✅ +45.3 | ✅ | ⚠ 全文无存储 API ⇒ 刷新即归零 |

⇒ 人工量的「−32px」与探针算出的「−27.5px」是同一件事；**死按钮的根因（歧义 `[data-close]`）第一次被机器抓到**，
不需要再靠人眼追 DOM 顺序。

**③ 接进流水线 —— 待落地，但先别当硬门禁**

上面三条判据已经全部可静态判定 ⇒ 天然满足「模型无关」。但**不要立刻抬成 P1 门禁**：
弱/本地模型的几何本就粗糙，硬门禁会让它每个 run 都红 —— 与 `0d` 保持 observation-only 是同一个理由。
建议顺序：先落进 `logs/teamflow/<runId>/scripts/` 作证据留痕、让 acceptance 阶段看得见，**攒够样本量再决定要不要抬成 P2**。

**④ 分层开关（craft 什么时候关）—— 新加，但本样本既证不了也证伪不了**

| 场景 | 倾向 | 理由 |
|---|---|---|
| 强模型 | 可关 | 条款是「约束它本来就会做的事」⇒ 倾向纯成本 |
| 弱 / 本地模型 | 建议留开 | 条款是「固化下限」⇒ 倾向净收益 |

- 成本量级上 craft 只多 +31% input，相对流水线 45× 的固定开销是噪声 ⇒ **不该因为它改架构决策**；
  同理，也不该因为本样本上 A 输 2 分就去删它（见 0.4：A 那两条「死按钮 / 不落盘」根本与 craft 无关）。
- 用法：`TEAMFLOW_CRAFT=0` 关闭（**缺省＝开**，老行为不变）；开关矩阵由 `test/craft-link.check.mjs` 守住。

**⑤ 下次验要换样本**

本次四维里三个接近满分、天花板效应明显；要选「组件数与数值彼此牵制更强」的需求（圆环/仪表盘/多状态卡片）。

### 0.6 读这份文档时最容易踩的三个坑

- **第 4 维不是持久化**。`ab-score.cjs` 只查「空闲态三项数字可见 + tabular-nums」，C 组也拿 5/5 却全文没有
  localStorage。看到「持久 5/5」必须另跑 `ab-persist.cjs` 才作数。
- **机器分是客观代理，不是美学判断**。它只判「存在性」，必须与人眼评分并列，不单独出结论。

  真实原因是用户跑的是短休（AC-11 设计）；更早还因为脚本只跑纯专注、从没模拟过切模式。

## 1. 为什么样本是番茄钟，而不是打砖块

| 考量 | 结论 |
|---|---|
| 阶段数能不能省 | **不能**。`design` 在所有档位都只认显式 flag（STAGE_POLICY：`when: (o) => !!o.needDesign`），而 `needDesign=true` 会被 triage 强制抬到 **medium**（prd/design/tech/dev/qa/acceptance 全跑）。换小需求省的是 dev 任务数与 QA 轮次，不是阶段数。 |
| 能不能省 token | **能**。番茄钟几乎没有业务逻辑（一个倒计时），dev 预计 1~2 个 task、QA 大概率 1 轮 ⇒ 单次估 600~1200 万 token，约为打砖块的 1/4。 |
| 信噪比 | **这是关键**。打砖块 4510 万 token 里大部分算力在碰撞/关卡/物理，对「视觉质感」这个待测变量是纯噪声；番茄钟的产出**几乎全部是视觉与交互**，差异不会被逻辑噪声淹没。 |
| 假阴性风险 | 样本退得太小会把效应量一起缩掉（差异消失 ⇒ 误判「4b 没用」）。番茄钟仍有四种状态 + 持久信息 + 动效，足以让三条 craft 条款都有发挥空间。 |

## 3. 跑法（A/B 只差一个变量；C 走原生单会话基线）

craft 开关走**环境变量**，不做工具参数（工具 `description` 每次都进主会话上下文，实测一段劝导语
492 字符 ≈137 tok；而这是临时实验开关，不值得常驻）。

```
# A 组：craft 开 —— 什么都不用做（缺省就是开）
dsh --profile web

# B 组：craft 关 —— 在**启动 dsh 的那个 shell** 里设变量
#   Git Bash:      TEAMFLOW_CRAFT=0 dsh --profile web
#   PowerShell:    $env:TEAMFLOW_CRAFT='0'; dsh --profile web
```

两组都跑同一个命令：

```
teamflow_start(requirement=<上面的需求>, needDesign=true)
```

要点：

- `needDesign=true` 必填：否则 design 阶段不跑，2b 这条最上游的通道根本不执行。
- 环境变量只认 `0` / `false` / `off` / `no`（大小写不敏感），未设置或空串都算开。
- **开关的取值会写进 run 快照**（`journal.options.craft`），所以事后仍能看出哪组是哪组；
  反过来 **resume 读的是快照、不是当前环境变量** —— 实验期间即使重启宿主，已开跑的 run 也不会半路变卦。
- `craft=false` 只关闭三处引导/观察条款（2b/4b/0d），任何 host 强制契约不受影响（契约测试有断言锁住）。
- ⚠ **上岗验证（比"磁盘源码改没改"可靠）**：craft 走环境变量这件事，只有当
  `teamflow_start` 的**参数列表里不再出现 `craft`** 时才算真的上岗。

  ```bash
  node .workbuddy/deploy-check.cjs    # 应显示「陈旧 0」
  # 重启后在宿主里看 teamflow_start 的参数清单：应当只剩
  # requirement / teamId / needDesign / needScaffold / ... —— 没有 craft
  ```

  为什么必须核这条：在环境变量版上线之前，已部署的 bundle 里 `craft` 是**工具参数**且完全不读
  环境变量 ⇒ 那时设 `TEAMFLOW_CRAFT=0` 毫无作用，A/B 两组吃的是同一份 prompt，
  测出来必然是「无差异」——而这个"无差异"会被误读成"craft 条款没用"，属于事后圆不回来的结论。
  ⇒ 若这一条没通过，两组数据一律作废，别填表。

- **怎么立刻知道环境变量生效了**（不用等流水线跑完）：pipeline 建 run 时就把 `options.craft` 落盘，
  实测 startedAt 后不到 1 分钟、stages 还空的时候就已经可读。所以：

  ```bash
  # 先跑这条（它会等新 run 落地），再去另一个窗口启动 dsh 并发 teamflow_start
  node .workbuddy/ab-run-check.cjs --wait=off     # B 组期望 craft=false；A 组用 --wait=on
  ```

  命中后它直接打印「期望 false / 实际 X」。若实际是 `true`，说明宿主进程仍加载着旧 bundle，
  重启 dsh 重开一个 run 再验，这一组数据作废 —— 别等到跑完才发现白烧一轮。

## 4. 判定：盲评打分表（先钉锚点再打分）

产物目录随机改名 A / B，不看来源、不对照 DIFF，**只看成品**。四维度各 1–5 分，每维都有行为锚点，
避免出现「看着还行给 4 分」这种漂移。

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| **表面处理** | 纯色矩形 + 系统默认边框，按钮无描边无圆角 | 有圆角与配色区分，但缺少描边/层次中的一项 | 圆角、描边、层次（背景/卡片/强化色）齐备，且数值一致不自相矛盾 |

## 5. 怎么解读结果（先把话说死，避免事后圆）

> ⚠ 本节口径在**补上第三组 C（dsh 原生单会话基线）之后**重写过。原文只写了两轴（A vs B），
> 现在实际是**两条正交的轴**，混在一起读一定会圆错。

- **单次只能给方向性证据，不能给统计显著性**（n=1/组）。本轮目标是判断「值不值得继续投入」，不是终审判决。

- **两条轴必须分开读**：

| 轴 | 对比 | 测的是什么 | 本轮结论 |
| --- | --- | --- | --- |
| 轴一：有没有流水线 | C vs B | 流水线的**固定开销**（多阶段 / 多 agent 的固有成本） | 便宜 **45×** input、**27×** 墙钟，分数只低 4 分 ⇒ 小活上流水线不划算 |
| 轴二：流水线内开不开 craft | A vs B | craft 条款的**边际收益 vs 边际成本** | input **+31%** / 调用 **+47%** / 墙钟 **+29%**，换来**更低的分** ⇒ 边际收益不抵成本 |

- **轴二沿用下面这组维度判读**（本轮它落在「流水线内部」这个前提上）：
  - 两组**四个维度都 ≥4 分** ⇒ craft 条款在这个场景没有可观测收益，倾向于移除。**但要先把需求复杂度提上去再验一次**，否则很可能撞了天花板效应。
  - **A 组总分显著高于 B（差 ≥4 分）且差距集中在第 3、4 维** ⇒ 支持「2b/4b 有用」，保留。
  - **差距集中在第 1、2 维** ⇒ 更可能是 dev 依 design 打磨（4b）在起作用，而 design 上游（2b）贡献有限。
  - **两组都很低（≤8）** ⇒ 瓶颈不在 prompt 条款，回头查 design 产物本身（DESIGN.md 是否真按 2b 写出了可执行数值），不要继续加条款。

- ⚠ **第 4 维是「可见性 proxy」，不是持久化**。`ab-score.cjs` 只查 `idle.time / idle.round / idle.today + tabular-nums`。
  看到「持久 5/5」**一律不能当持久化通过** —— C 组这一维同样是 5/5，可它全文 0 次 `localStorage`，
  「今日专注 / 轮次」是内存变量、刷新即归零。真持久化必须另跑 `ab-persist.cjs`（三组中**只有 B 通过**）。
  同理，四维总分也不能单独出美学结论，必须与人工评分并列。

- ⚠ **别把「C 便宜」读成「流水线没价值」**。C 满足的是「能跑起来」，不是需求 AC：它丢了持久化、
  也没做模式切换后的统计口径保护。正确表述是 **「便宜但有功能缺口」**，不是「更划算」。
  可比的是**单位质量成本（分数 ÷ input）**，不是绝对值。

- 无论结果如何，都要连同 `logs/teamflow/<runId>/` 归档里的 DESIGN.md 一起归档进来：它是判断
  「是通道没通，还是通了但模型没照做」的唯一证据。

## 8. 机器评分：同一浏览器的客观代理（`ab-score.cjs`）

人眼评分会漂移（同一份东西隔一天再打常差 2 分），所以用真浏览器把四维度换成可复算的事实。
出发点还是项目那条「能由 host 客观判定的，就不要依赖模型自律」——评审环节同样适用。
**它不取代人眼，只做交叉验证。**

| 原始事实 | Sample-A | Sample-B |
|---|---|---|
| 按钮数 / 有圆角 / 有描边或阴影 | 7 / 7 / 4 | 7 / 7 / 6 |
| 背景色种数 / 圆角块数 | 6 / 10 | 4 / 8 |
| CSS 状态规则 hover / active / focus / disabled | 5 / 4 / 3 / 10 | 3 / 1 / 1 / 3 |
| 自定义 focus 指示 | 3 | 1 |
| 过渡元素 / 动画元素 / 进度环元素 | 8 / 0 / 2 | 9 / 2 / 5 |
| 空闲态 时间 / 轮次 / 今日次数 / 等宽数字 | 全可见 / 是 | 全可见 / 是 |
| **【校准项】环 vs 数字几何重叠** | 内半径 113，数字最远角 145 ⇒ **余量 −32px（压到环线）**，字号 94.68px | 内半径 101，数字最远角 59 ⇒ 余量 +42px（在环内） |

校准项是怎么来的：先由人眼指出两条肉眼差异，再回头把它翻译成可复算的几何/运行时事实，机器才复现出来了。
**纯靠第一版仪器是看不见这两条的** ⇒ 仪器得由人眼先提假设、再由机器把假设钉死，二者缺一不可。

⚠ **这一版仪器的两个诚实缺陷**：

1. **天花板效应**：顶档只靠「存在性」就能拿满分（有 hover 规则 = 5 分），两组在三维度上打平 ⇒
   这套 1/3/5 桶**分辨率不够**。真正有区分力的是上面的**原始计数**（状态规则数与配色丰富度差距明显），
   判读时要用原始计数做并列破除，别只盯总分。
2. **机器不是美学**：它判的是「有没有」，不是「好不好看」。这两个不等价 —— 数值自洽的圆角未必好看，
   缺 hover 也未必难用 ⇒ 机器分必须与人眼分并列呈现，不得单独出结论。

## 9. 持久化取证：今天的数字，刷新后还在吗（`ab-persist.cjs`）

第 4 维「持久信息可见性」只判了**空闲态能不能看见**，没判**刷新后还在不在** —— 而后者才是用户真正会在
第二天感知的差别。补一层取证。（脚本三条子命：`round` / `storage` / `crossday`。）

> **不用真等 25 分钟**：两边都是「每次取 `Date.now()` 算剩余」的时间戳实现，
> 把 `Date.now` 乘 4000 倍，一轮几秒就跑完。若某实现改成按 tick 数拍子，脚本会报 `已加速=false` 而不是假装通过。

```bash
node .workbuddy/ab-persist.cjs round       # 加速一轮 → 是否落盘 → 重载能否恢复
node .workbuddy/ab-persist.cjs storage     # 定位落盘失败到底卡在哪
node .workbuddy/ab-persist.cjs crossday    # 播种昨日的记录 → 是否跨日清零
```

| 检验 | Sample-A | Sample-B |
|---|---|---|
| 加速一轮后 UI 计数 | 正确（`轮次 2 今日专注 1` + 完成弹窗） | 正确（`轮次 2 · 今日专注 1`） |
| **localStorage / sessionStorage** | **全空 `{}`** | **`pomodoro:stats:v1 = {date,focusCount:1,round:2}`** |
| 重载后 UI | 退回 `轮次 1 今日专注 0` | 仍是 `轮次 2 · 今日专注 1` |
| 播种昨日 count=7 后 UI | 显示 0 **但磁盘原值没被改写**（见下） | 显示 0，并回写成今日 `{focusCount:0,round:1}` |

### Sample-A 为什么"看起来对"却完全不持久

`'storage'` 子命把故障 isolate 到具体一行：

```
hasGlobalRoot:      false          // 浏览器里没有全局 root
rawLocalStorage:    "x"            // 裸 localStorage 在这个环境完全可写 —— 不是浏览器/沙箱的锅
viaAppStore:        null           // 走它自己的封装写 → 读不回来
afterDefiningRoot:  "{...count:1}" // 手动 window.root = window 后立刻正常落盘
```

根因（`Sample-A/storage.js:14-20` 的 UMD 包装）：

```js
(function (root, factory) { ... })(typeof self !== 'undefined' ? self : this, function () {
  // 工厂函数是在**调用方作用域**里定义的 ⇒ 这里的 root 不是上面那个形参
  try { root.localStorage.setItem(probe, '1') } catch (e) { usable = false }   // TypeError → 静默降级内存
})
```

浏览器里 `root` 解析到未定义的全局变量 ⇒ probe 抛错 ⇒ `usable=false` ⇒ **全程走内存后端**。
于是：UI 计数看着是对的（内存里对的），`try/catch` 全程静默，重载后归零。
而且 `tests/storage.test.js` 恰好是显式注入**内存 backend** 做单测的 ⇒ **单测全绿，功能坏着**。

⚠ 这条对本实验的判读很重要：它属于**"写了持久化、也写了测试，但仍然不可持久化"**，
比"压根没做持久化"更有害 —— 因为它给出了虚假保证。人眼评审在这一项上**必然被骗**
（UI 显示完全正确，footer 还写着「数据仅存本机」）。

### 怎么落到第 4 维

第 4 维的锚点文字要按这份证据扩一句：原来是「空闲态数字可见且等宽」，现补
**「刷新后能恢复」** —— 否则 Sample-A 这种"看得见但存不下"照样满分。
复跑取证后由人眼决定是否据此改分；每行结论都必须能落到上面那张表的某一格。

2026-10-01 用户手动试用 A 组产物，报「倒计时结束后点『好的』没反应」。复现与定位（`ab-interact.cjs`）：

根因（`app.js:61` + `index.html:53/57`）：

```

```
⇒ `addEventListener('click', hideCompletion)` 落在遮罩上，**主 CTA 全程无 handler**。
B 组用的是 `getElementById('overlayClose')`（唯一 id），所以没踩。

**临时绕法**：点弹层外的遮罩区域即可关闭（但用户第一反应必然是点按钮）。

### ⚠ 我这次漏检了，教训要记下来

`ab-persist.cjs` 其实点过这个按钮，却**没有断言"点击是否产生了状态变化"**——它只关心存储内容，
点空了也照样往下走。加上 `ab-score.cjs` 只看静态与几何，两套仪器**都没覆盖交互功能**。

⇒ 补两条硬纪律：

1. **交互探针必须断言状态变化**："点了"≠"生效"。每次 `.click()` 之后都要断言预期状态
   （弹层关闭 / 计数变化 / 写入发生），否则等于没测。`ab-interact.cjs` 现在就是这么写的。
2. **合成 `.click()` 不等于用户点击**：程序化点击绕过了命中测试，遮挡/指针事件/绑错对象这类问题
   它照样"点得动"。要覆盖真实可点性，得断言状态变化（能抓到绑错对象），
   真要验证遮挡则要用 CDP 派发真实鼠标事件。

### 对判决的影响

**不改变排序**（A 本来就落后），但把 A 的问题从「视觉/持久化」扩到**功能可用性**：
至此 A 组共 3 类可复现缺陷——环线压数字、`好的`死按钮、今日累计不落盘；B 组 1 类（运行中可切模式会重置计时）。
另注：`ab-persist.cjs` 那条持久化结论**不受本次漏检影响**，因为它同时用 `storage` 子命直接调用
`PomodoroStore` 取过证，与按钮点击无关。
## 12. 揭盲后 B 组「focusCount 没 +1」的追查（用户实测）

用户手动在 r2（craft 关）跑完一轮专注后 `focusCount` 没加，Console 读到：

```json
{"date":"2026-10-01","focusCount":0,"round":1}
```

### 12.1 先坐实：这条记录说明了什么

| 观察 | 代码位置 | 推论 |
| --- | --- | --- |
| 记录存在且 date = 今天 | `app.js:367-368`（init 即 `maybeResetDaily(loadStats())` + `saveStats`） | **打开页面就会写入今日零值** ⇒ 「记录存在」不携带任何完成信息 |
| `focusCount:0 / round:1` 恰是初值 | `app.js:74 / 76` 默认值 | 判据只能是数值本身 |
| 走 focus 分支必然写 `focusCount:1 / round:2` | `app.js:214-219`；加速跑与真实节奏跑两处都实测复现该值 | ⇒ **该页面实例里 focus 完成分支从未执行** |

排除项：完成之后只有 `onOverlayClose → timer.reset`，不碰 stats；`maybeResetDaily` 只在跨日时归零；
全文件没有第二处会把值写成 0。⇒ 此前列的第 3 种（存储不可写）**当场排除**——读得回来就说明可写。

### 12.2 剩下两类，各对应什么

1. **那一轮其实不是以专注模式跑到 0** —— 与 B 的已知缺陷同向，首因判据押这条。
2. **完成从未在该页面实例发生** —— 结束前被关掉/新开过，或机器睡眠期间定时器没跑。
   我的三种模拟（真实节奏、`setInterval` 节流 60s、file:// 开/关 allow-file-access）都复现不了，
   但它们只证明**我模拟的那几条路径是对的**，不证明真实环境不发生。

### 12.3 需要一句话判别（任一即可定位）

- **（a）** 弹层写的是「专注完成 🎉 已计入今日」，还是「短休完成 / 长休完成」？
- **（b）** 看值那一刻界面是 **00:00 + 弹层**（那轮确实跑完并被关掉），还是已经回到 **25:00 idle**（页面重新开过）？
- **（c）** 有没有在**另一个窗口 / 无痕 / 别的浏览器**里打开过这个页面？init 就写零值 ⇒ 新开的窗口会立刻
  把 `0/1` 写回去，读那个窗口永远看不到完成。
- **（d）** 中途有没有点过 **短休 / 长休** ？（`app.js:173 setMode` → `timer.reset` + 改 `state.mode`，
  切过之后跑完的是休息，AC-11 只累计专注）

### 12.4 首因判断（未坐实，等（a）一句话）

`setMode` 会重置计时器并改 `state.mode`，而 **B 组恰恰是唯一允许运行中切模式的那一组**
（A 在开始后把三个模式按钮 disabled）。只要中途切过一次短休/长休，那一轮结束时 `state.mode !== 'focus'`，
`focusCount += 1` 被整段跳过 —— 症状与用户描述完全吻合。

这也解释了我此前的模拟为什么全都复现不出来：**脚本里只跑纯专注，从来没在模拟中切过模式**。
⇒ 教训（比 bug 本身重要）：**模拟必须先复刻用户的操作序列，而不只是覆盖代码路径**。
三条排除实验只证明了「纯专注路径正确」，我却把它误当成了「B 的计数没问题」。

> 该结论不参与 A/B 排序：B 本来就领先，且这条与「B 唯一缺陷 = 运行中可切模式会重置计时」同向，
> 属于**同一处代码的两面**（切模式既重置计时、又绕过统计口径），反而强化了那条缺陷。

### 12.5 用户回证：那个弹层是 A 组的短休，不是 B 的专注

用户回：弹层显示「短休完成！ / 第 1 轮 · 休息结束，准备下一轮」。代码对照给出决定性证据：

### 12.6 一击定案的「哨兵值」判别（推荐用户执行）

在 B 页跑一轮**之前**，先往存储里塞一个不可能自然出现的值，跑完再读：

```js
localStorage.setItem('pomodoro:stats:v1', '{"date":"2026-10-01","focusCount":999,"round":999}')
```

| 跑完读回来的值 | 结论 |
| --- | --- |
| 仍是 `999 / 999` | 完成分支**没跑**（那一轮不是专注，或根本没跑到 0） |
| `focusCount:1 / round:2` | 计数逻辑正常 ⇒ 之前那轮确实不是专注（哨兵被正确覆写） |
| `0 / 1` | 只跑了 `maybeResetDaily`（页面重开 / 回前台）而完成**没触发** |

好处：不受「页面是不是被重开过」「是不是看错窗口」干扰，一次运行即可分辨。

### 12.7 哨兵值截图：这张图只可能是 B 组页面（并反证 A 的存储确实坏着）

用户回图：底部显示「轮次 999 · 今日专注 999」，模式=专注，25:00，idle 态。

| 侧 | 底部数据来源 | 能否显示 999 |
| --- | --- | --- |
| A（r1） | `r1/app.js:28` `round` 是**内存态**（注释即「刷新归 1」）、`r1/app.js:233` `el.roundVal = state.round`；今日专注走 `store.getToday().count`（`r1/app.js:232`）＝坏掉的 store ⇒ 恒 0 | ❌ **不可能** |
| B（r2） | `r2/app.js:306-307` `roundVal / focusCount = state.stats.*`，`state.stats` 来自 init 的 `loadStats()` ⇒ 直接读 localStorage | ✅ |

⇒ 「轮次 999 · 今日专注 999」能出现在 UI 上，**只可能是 B 组页面**；这条顺带给 A 的「不落盘」补了一层
**UI 级运行时佐证**（此前证据是探针隔离 + `afterDefiningRoot` 有值）。同样操作在 A 页做一次，A 只能显示

截图还是 **idle 25:00**（`开始` 未点 ⇒ 这一轮还没开始），所以下一步判据很干净：这页直接点「开始」跑满
25:00（**中途不要刷新/关闭**，否则 deadline 在内存里会丢、回 25:00），跑完立刻读
`localStorage.getItem('pomodoro:stats:v1')`：

| 结果 | 结论 |
| --- | --- |
| UI → 轮次 1 · 今日专注 1，读回 `focusCount:1 / round:2` | 全链路通 ⇒ 之前那轮**确实不是专注** |
| 读回仍是 `999 / 999` | 完成分支**根本没跑** ⇒ B 的真缺陷信号（我此前三条模拟复现不出来，正因脚本只跑纯专注） |
| 读回 `0 / 1` | 只走了跨日归零分支（date 相同则不会，概率低） |

### 12.8 哨兵读回 `999 / 999`：focus 分支这一轮确定没执行

用户跑完专注后读回仍精确等于哨兵值 `{"date":"2026-10-01","focusCount":999,"round":999}`。
这个观察**比"999 没变"更锐利**：只要 focus 分支跑过一次，`focusCount += 1` / `round += 1` 必然写成
`1000 / 1000`（`r2/app.js:216-219` 后紧跟 `saveStats`）。⇒ **该轮结束时 `state.mode !== 'focus'`，
或 `handleComplete` 根本没执行**。

同时排除掉两侧伪因：
- **不是存储坏了**：值能被读回来、截图里 UI 也从 `0/1` 渲染成 `999/999` ⇒ 读写与「存储→UI」都通。
- **不是 `phase` 守卫卡死**：`phase` 在 `setMode`(179) / `reset`(200) / `onOverlayClose`(206) 都会置 `idle`，
  守卫（211 行「弹层未关不重复计数」）只在弹层未关时生效。
- ⚠ 但顺带挖出一条**真缺陷**：`r2/app.js:184` `if (phase !== 'idle' && phase !== 'paused') return;`
  ⇒ **上一轮弹层没关时，点「开始」会被整个忽略**（连计时都不起）。若用户是这么卡住的，
  那一轮确实永远跑不到 00:00 —— 与「完成没触发」的观察吻合。

⇒ 失败面缩到两处：(a) 结束时 mode 不是 focus（切过模式 / 开始时就选的短休）；
(b) 那一轮压根没在**这个**页面实例跑到 00:00（弹层未关导致 start 被忽略、或页面后来被重开）。

### 12.9 升级版哨兵：过期日期，一次跑开三态

上一版哨兵用当天日期，无法区分「完成跑了非 focus（saveStats 原样写回 999）」与「压根没跑」——
两者读回来一模一样。改成**过期日期**即可（`handleComplete:214` 会先 `maybeResetDaily` 跨日归零）：

```js
localStorage.setItem('pomodoro:stats:v1', '{"date":"1999-01-01","focusCount":998,"round":998}')
```

然后**只点开始、不要碰模式按钮**，跑到 00:00 再读：

| 读回 | 结论 |
| --- | --- |
| `{"date":"2026-10-01","focusCount":1,"round":2}` | focus 完成分支执行过 ⇒ B 计数链路正常，之前那轮不是专注（或没跑完） |
| `{"date":"2026-10-01","focusCount":0,"round":1}` | 写盘发生了但非 focus ⇒ 结束时 `state.mode !== 'focus'`（中途点过模式切换） |
| 仍是 `date=1999 / 998` | `handleComplete` 从没执行 ⇒ 那轮没真跑到 00:00（大概率是弹层未关导致 start 被忽略 / 在别的页面跑的） |

> 若落第三态，B 的缺陷就从「统计口径」升级到**交互栅栏缺失**：上一轮弹层不关 ⇒ 新一轮点开始无反应
> 且**界面上没有任何提示**（开始按钮只是不被响应，不 disabled）。这条值得单独记一笔。

### 12.10 收尾：B 的「focusCount 没 +1」结案，产物冻结留存

**结案**：用户确认那一轮跑的**是短休不是专注**（「专注太久了」）。
`r2/app.js:215` 的 `if (state.mode === 'focus')` 未进入 ⇒ `focusCount` 不增是 **AC-11「仅专注模式累计」的
设计行为，不是缺陷**。此前三条模拟全部复现不出来，正因脚本只跑纯专注、从未模拟用户跑休息。
⇒ B 组缺陷清单定稿为 1 条（运行中可切模式会重置计时；`app.js:184` 弹层未关时「开始」被静默忽略且
无 disabled 提示），A 组 3 条。**排序不变，本条追查对判决零影响。**

### 18.3 怎么读这组数

1. **在这个任务上流水线不是必需的**：C 只花 1/45 的 input、1/27 的墙钟，机器分只低 4 分（18→14），
   且环线不压数字、空闲三项可见、完成提示用 toast 做了。**印证了「单需求单 agent 直干」的判断。**
2. **但 C 便宜 ≠ 等价**：C 丢了**持久化**（无 localStorage）、没做模式切换后的统计口径保护，
   满足的是「能跑起来」，不是需求 AC。⇒ 正确表述是「便宜但功能缺口」，不是「更划算」。
3. **craft 条款的作用面被精确落到「反馈」维度**：hover/active/focus/disabled 规则数
   **C = 0/1/0/0 → B = 3/1/1/3 → A = 5/4/3/10**，是 0→3→5 的单调梯度 ⇒ 条款确实在它该干的岗位上干活；
   问题是它的**边际成本被流水线的固定开销淹掉了**（45 倍里它带来 input +31% / 调用 +47% / 墙钟 +29%）。
4. **两条轴要分开看**：轴一「有没有流水线」（C vs B）= 固定开销 45 倍；轴二「流水线内部开不开 craft」
   （A vs B）= craft 自身的边际开销，而**换来的是更低的分**。
   ⇒ 本样本上：**流水线固定开销 ≫ craft 边际开销，craft 边际收益不足以覆盖自身成本。**
5. **仍别删条款**：A 输给 B 的原因（环压数字 −32px、死按钮、不落盘）全部指向「规格不自洽 +
   无运行时自校验」，与第 10 节一致——不是条款有害，是**下游没人判自洽**。
   处置仍是「把写详细升级成写完自洽」，外加**分层使用**：单需求/小改动走原生或 `patch` 档，
   需要质感下限 + 多阶段协作的长任务才上流水线；批量可靠交付才是插件的主战场。

⚠ 全部 n=1/组；A/B 的 input 含 QA 拦下 P1 那一整轮 rework 与 dev 9 波 vs 4 波的分歧；
C 只跑一次且未经过 design 阶段（它是「无流水线」，不是「流水线但关条款」，不能当 B 的对照组）。
