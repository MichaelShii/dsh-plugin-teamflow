# TeamFlow 执行路径基准（pipeline vs 原生 DSH）

> 同一需求、同一基线、两种执行路径的横向测量。
> 目的：量化「编排流水线」相对「让模型直接干」在时间 / token / 调用 / 质量上的差异，
> 为 TEAMFLOW 的拆分与上下文策略提供实证依据。

## 实验设置（2026-08-20）

| 项 | 值 |
|---|---|
| 需求 | Tetris 本地持久化（P2 转 P0）：最高分 + 音量/静音 localStorage 持久化 |
| 产品基线 | `main`（BGM v2.5，`774abca`，**未实现持久化**） |
| 路径 A | TeamFlow 流水线（lite + 软件开发团队，run `tf-mt1es4en-5cekmf`） |
| 路径 B | 原生 DSH 单会话（新分支 `feat/persistence-localStorage-main`，从 main 拉） |
| 对照控制 | 同基线、同需求；路径 B 明确不读流水线旧分支（但实测跑过 `git diff main feat/persistence-localStorage`，存在轻微变量污染，见下） |

## 结果对比

| 指标 | 路径 A（流水线） | 路径 B（原生 DSH） | 差异 |
|---|---|---|---|
| 总耗时 | 38 分钟 | 27 分钟 | **B 快 29%** |
| 模型调用次数 | 164 次 | 115 次 | **B 少 30%** |
| billed token（≈） | **11.6M** | 19.1M | **A 省 39%** |
| ├ input（未命中） | 327k | 395k | A 略省 |
| ├ cacheRead（命中） | 11.2M | 18.7M | **A 省 40%** |
| └ output（输出） | 110k | 64k | A 多（多阶段多报告） |
| 缓存命中率 | 97.2% | 97.9% | 相当 |
| 消耗 token / 调用 | ~70k | ~166k | **A 高效 2.4×** |
| 工具调用 | 6 子代理（结构化） | 119 次（56 edit / 28 pwsh / 28 read / 2 write / 1 grep） | — |
| 交付产物 | v2.6，19 文件 | v2.6，19 文件（含新 `storage.js` 297 行 + `verify-storage.cjs` 187 行） | 范围相当，架构不同 |
| 质量（功能） | 七套验证全绿，验收 ✅ | 七套验证全绿（52/23/8/9/2/装配/204），独立实现 | 功能等价 |
| 质量（代码架构） | **见 §代码质量深度对比（流水线显著更弱）** | **见 §代码质量深度对比（原生显著更强）** | **B 强** |

## 关键发现

1. **流水线调用更多但每次更便宜**；原生单 agent 少调用但每次贵 2.4×。
   - 流水线 164 × ~70k ≈ 11.6M
   - 原生 115 × ~166k ≈ 19.1M
   - 根因：**上下文隔离**。流水线把任务分给多个子代理，每个只读自己的文件（干净上下文）；原生单 agent 28 次 read 把 game.js/audio.js/ui.js/storage 读进后上下文无限膨胀，后续每次调用都背着 18.7M 缓存前缀。

2. **拆分 / 多子代理的价值在「上下文隔离」，而非「并行调用次数」**。
   - 流水线即使某阶段是「整体开发」，仍比原生单 agent 省，因为阶段间上下文不复用。
   - 印证「拆分 + 避免记忆重复」方向：拆得对（按文件边界、无并发冲突、上游已梳理完）才有效。

3. **原生更快**：无 QA/验收门禁和文档沉淀，少几次串行阶段；但代价是上下文膨胀更费 token。

4. **「功能等价」≠「代码质量等价」**：两条路径都交付全绿 v2.6，但**代码架构质量差异显著**（原生更强）——详见下节。只看 verify 全绿判「质量等价」是错误结论。

## 代码质量深度对比（新增，修正「质量等价」的错误判断）

> 不止看 verify 全绿，逐项对比两条分支的实现架构、DRY、边界、可测性、装配。

| 维度 | 路径 A（流水线） | 路径 B（原生 DSH） | 谁更强 |
|---|---|---|---|
| **架构 / 模块化** | localStorage 散在 game.js + audio.js + ui.js 3 处，无独立模块 | **独立 `storage.js`（297 行，UMD 工厂 + 闭包）统一封装** | **B 强** |
| **DRY（代码重复）** | game.js `safeStorage` + audio.js `resolveStorage/storageGet/storageSet` **两套几乎重复的适配器** | 单点 `createStorage`，无重复 | **B 强** |
| **单一事实来源** | 键名分散：game `tetris.highScore`、audio `tetris.volume/muted` | `PERSIST_DEFS` 集中定义键名/默认值/解析器 | **B 强** |
| **异常 / 边界** | 都有安全适配器降级、非法值校正、抛错测试 | 更系统：后端抛错/配额/缺失 → 统一降级内存兜底 | B 略强 |
| **可测试性** | DI 注入 storage；verify-game 有抛错后端测试；但 **verify-audio 未测 localStorage 写入/恢复** | `createStorage({backend})` 注入；verify-storage 专测：导出面/键唯一/跨实例读回/非法值/抛错降级/内存兜底（+9 项） | **B 强** |
| **装配 / 契约** | 无统一导出面，依赖内部函数 | UMD `window.TetrisStorage`；index.html 明确 audio→game→storage→ui 装配顺序 | **B 强** |
| **dispose 清理** | 依赖各模块既有 dispose | storage 明确 dispose、无泄漏测试 | **B 强** |
| **产出规模** | +948/−347，3 处散改 | +860/−51，新增独立模块 | B 更收敛 |

**结论：原生路径代码质量显著更高**——模块化、DRY、单一事实来源、专测覆盖、清晰装配都优于流水线这次的整体开发。

## 教训（为什么流水线代码质量低了）

1. **省 token ≠ 牺牲架构**。流水线这次是 lite 模式的「整体开发」单任务，且 TOKEN_HYGIENE 引导 dev「只读任务内文件、别整读大文件」→ dev **失去全局架构视野**，想不到「该抽独立 storage 模块」，于是散落重复。
2. **记忆共享补不到「架构意图」**：现有 state.json 共享的是「结论摘要/模块一句话契约」，不存「为什么这么架构、模块依赖、装配顺序」。dev 拿到的是模块罗列，不是架构蓝图。
3. **tech 阶段是代码质量的生命线（核心教训）**：lite 为了省 token 跳过了 tech 阶段，结果省了架构、费了质量。架构拆解（该抽什么模块、怎么装配、依赖方向）必须由 tech 阶段产出并注入 dev，不能靠 dev 自己零散读文件重建——这与「tasks 由技术阶段拆、PRD 只管大方向」是同一原则。

> **参照基线**：原生 DSH 的高质量工作流拆解见 [`native-workflow.md`](./native-workflow.md)（环境探索 → 全局 READ → Design Decision → 基线验证 → 实现）。流水线引入团队概念应以它为蓝本，在「Design Decision」点映射架构角色，而非凭空造层。

## 结论

- **想省 token（降低成本）→ 流水线**（省 ~39%，靠阶段/子代理上下文隔离）。**但必须以不牺牲代码质量为前提**：代码质量是生产底线，不能为省 token 放弃架构。
- **想快 + 轻 → 原生 DSH**（快 ~29%，少门禁；单 agent 上下文膨胀可控时，轻小需求更值）。
- **拆分的正确动机是上下文隔离，不是并行度**；并发的前提仍是无文件冲突 + 上游梳理完。
- **流水线要保质量，tech 阶段（架构设计）不能省**。省 token 的正确方式是把 tech 阶段产出的「架构蓝图（模块/依赖/装配/理由）」注入 dev，让 dev 在已有架构上实现，而不是跳过 tech 让 dev 自己零散读文件重建架构——否则 token 省了、架构塌了（本次实证：流水线输出两套重复适配器，原生输出独立模块）。

## 局限与变量

- **变量污染**：路径 B 实测执行了 `git diff main feat/persistence-localStorage --stat`，看到了流水线旧分支，可能参考其上下文 → B 非 100% 干净基线；但仍产出独立实现（storage.js 等，流水线那次没有）。
- 单次测量，LLM 有随机性；严格结论需多轮取均值。
- 需求复杂度本身影响绝对量，跨需求对比不成立（如 BGM 与持久化不可直接比）。

# 复核：ADR-0006「认知前置 + 架构落地」后的干净对照（2026-08-21）

> 历史 A/B 之后，TeamFlow 做了 ADR-0006（M0 状态核对 / M1 架构蓝图全模式启用 / M2 dev 按蓝图拆任务 / M3 QA+验收架构核验 / triage 架构护栏）。
> 本节用**同一条持久化需求、从零实现**的第三个数据点，测量该重构后流水线的质量与成本，并验证「tech 阶段是质量生命线」的教训是否被修正。

## 实验设置（复核）

| 项 | 值 |
|---|---|
| 需求 | 同历史：Tetris 本地持久化（最高分 + 音量/静音 + **幽灵/BGM 四设置**）从零实现 |
| 产品基线 | `main`（BGM v2.5，`774abca`，未实现持久化）——与历史 A/B 相同 |
| 路径 C | TeamFlow 流水线 **`tech` 档**（架构蓝图全模式启用，run `tf-mt317a5e-0iwvuy`） |
| 对照纯度 | **比历史 A/B 更干净**：全新分支 `feat/persistence-localStorage2`、M0 状态核对通过（工作区仅 `.idea/` 未跟踪）、严禁参考任何旧分支/`.tmp-zst` 残留 |

## 结果对比（三路径并排）

| 指标 | A 历史流水线（lite） | B 历史原生（DSH） | C 本次流水线（tech） | 差异 |
|---|---|---|---|---|
| 总耗时 | 38 分钟 | 27 分钟 | **~19 分钟** | **C 最快**（较 A −50%，较 B −30%） |
| 模型调用次数 | 164 次 | 115 次 | **217 次** | C 最多（6 并行 dev 任务 + QA + 验收） |
| billed token（≈） | 11.6M | 19.1M | **10.2M**（input 425k + cacheRead 9.78M） | **C 最省**（较 A 再省 ~12%，较 B 省 ~46%） |
| cacheRead（命中） | 11.2M | 18.7M | 9.78M | C 最低 |
| output（输出） | 110k | 64k | 134k | C 最多（多阶段多报告） |
| 缓存命中率 | 97.2% | 97.9% | 95.8% | 相当 |
| 消耗 token / 调用 | ~70k | ~166k | **~47k** | **C 最高效**（较 A ×1.5、较 B ×3.5 更省/调用） |
| 交付产物 | v2.6，19 文件 | v2.6，19 文件（`storage.js` 297 行） | **`persist.js` 14KB（359 行）+ `verify-persist.cjs` 200 行 + T1~T6 六任务** | 范围相当，架构不同 |
| 质量（功能） | 七套全绿，验收 ✅ | 七套全绿，验收 ✅ | **六套既有 + verify-persist 全绿（52/23/7/2/装配ALL/188 + 10/10），但验收 ❌ 打回** | C 暴露 P1 |
| 质量（代码架构） | 弱（两套重复适配器） | 强（独立 storage.js） | **强（独立 persist.js，单一事实来源，无重复适配器）** | **C 对齐 B** |

## BUG-P1-1（本次新捕获的真实缺陷，也是最重要发现）

> 六套既有验证 + 新 verify-persist **全部通过**，但 QA 用独立对抗探针（注入**真实 localStorage API 形状**，仅 `setItem/getItem/removeItem`）复现核心功能在真实浏览器完全失效：

- **缺陷**：`persist.js` `createStorage` 能力探测用 `setItem/getItem/removeItem`（探针成功 → `available=true`），但返回适配器内部却调用 `store.set/get/remove`（内存 Map 的 API 形状）——原生 `localStorage` **没有**这三个方法 → 每次读写抛 `TypeError` 被 try/catch 静默吞掉，且因 `available=true` **不降级内存** → 持久化在真实 `file://` 浏览器完全静默失效（AC-16 最高分 / AC-10.5 四设置 reload 全丢）。
- **根因（测试盲区）**：`verify-persist.cjs` 注入的 `makeBacking` 恰好实现了 `get/set/remove`，与适配器内部调用**同构** → 单测全绿掩盖真实断链；jsdom E2E 无持久化断言也未拦截。
- **拦截链路**：QA 独立对抗 + **M3 架构核验**（「适配器实现与契约偏离 = 适配器漂移」列为门禁拦截项）+ 验收**源码复核**（产品经理直接读 `persist.js` 108-164 行确认，非仅采信 QA）→ 三层独立捕获同一缺陷并打回。
- 已按打回要求回写 `memory.md`（v2.6 打回记录 + 待办打回项），修复方向：`createStorage` 统一调用面为 `setItem/getItem/removeItem`（薄层映射）+ verify-persist 补真实 API 形状对抗用例。

> ⚠️ **流水线登记日志观察**：run 的 `logs` 尾行记为「QA 未发现 P0/P1/P2 缺陷（未登记 Bug）」，但 QA 阶段产出与验收结论均为「打回 BUG-P1-1」——日志与阶段产出不一致（疑似缺陷登记口径未随 QA 产出更新），真实性以 QA/验收阶段产出为准；建议核查 bug 登记路径。

## 关键发现（复核落地）

1. **架构质量反转（ADR-0006 主要目标达成）**：tech 前置 + M2 按蓝图拆 6 个并行任务 → 产出**独立 `persist.js` 模块、零重复适配器**，架构质量对齐历史原生 B，直接修正历史「流水线代码质量显著更弱」的结论。M1（蓝图全模式启用：拆出 6 任务含依赖/装配序/重复告警）与 M2（T1<T2/T3/T4 依赖链 + 并发 3）实证生效。
2. **「全绿 ≠ 可用」在流水线自身复现，且被三层门禁正确拦截**：与历史 §「只看 verify 全绿判质量等价是错误结论」同源，但这次是**流水线自己的 QA + M3 + 验收**在交付出口前拦住，而非事后人工审计——**质量门禁自动化的价值被实证**。
3. **验证脚本与实现「同构伪造」是新的盲区**：测试注入的 fake storage 必须与真实 API 形状一致，否则全绿=假绿。这是对「测试策略」的普适教训（不限于流水线）。
4. **成本收益继续向下**：三层门禁 + 文档沉淀下，billed 仍三路径最低（10.2M）、耗时最短（~19m）；代价是调用数最多（217）——「上下文隔离 + 一次性共享认知」再次验证，且**多任务并行 + 质量门禁没有把成本垫高**。
5. tech 档（架构蓝图）与历史 lite（跳过 tech）构成同流水线内的前后对照：**认知前置管「怎么拆」（架构对），对抗测试管「真不真」（运行对）**——两者都不能省。

## 复核结论修正（相对历史）

- 「想省 token → 流水线」仍然成立且更优（C 比 A 再省 ~12%）。
- 历史「流水线质量 = lite 跳过 tech」的翻车点**已被 ADR-0006 修正**：tech 全模式启用后质量对齐原生。
- **新增的（尚未闭环）弱点**：test 与实现同构 → 假绿；修复后需复验（修复要求：真实 API 形状对抗用例 + 全表复跑 + 真实浏览器路径 AC-16/AC-10.5 生效），**一次验收打回置为流通**（req-4 仍在 `needs-human`，工作区未 commit）。
- 局限：C 为单次测量；修复复验数据尚未产出（本次打回即数据点结束）。
