# Agent 一阶段烧掉 5 万 token 零产出，真凶是一个 Windows 权限位

> 副标题：一次「环境故障伪装成模型故障」的完整复盘——从 52,588 token 的假 max-tokens，到控制变量实验锁定 `WRITE_OWNER`，再到流水线启动前的自动自愈。

## TL;DR

- 多 Agent 流水线在用户新建的目录里，第一个阶段就全灭，表现是「模型输出被 max-tokens 截断」——**真因是宿主沙箱的 Windows ACL 授权失败（Win32 5），一个模型完全无感的环境问题**。
- 第一版修法是止损：识别「环境不可用」就立刻停手，同一个场景从 **52,588 输出 token / 3 分 45 秒 / 零产出**降到 **1,510 token / 15 秒**——但每次都要人工排查修复，治标。
- 根因用一组**四态控制变量实验**定位：单一权限位 `WRITE_OWNER`。数据盘新建目录的继承 DACL 里没有当前用户的显式 ACE，owner 隐式权限不够写完整性标签。
- 最终修法是插件在流水线启动前**自动自愈**：用宿主自己的 ACL 包物化授权，缺权限时补一条只含 `WRITE_OWNER` 一个权限位的修复 ACE——**不需要管理员**。端到端实测：预检在第一个模型调用前打出修复日志，全 run 零授权错误。

## 一、现象：每个新目录，流水线第一步必死

背景先交代一句：我们的插件（dsh-plugin-teamflow）会在一次会话里拉起一支子代理团队，跑完「需求 → 技术方案 → 并行开发 → QA → 验收」的流水线。子代理要执行 shell 命令，而宿主（DeepSeek Harness）在 Windows 上给工作区套了一层 ACL 沙箱：第一次在这个工作区跑命令时，沙箱先给目录物化一条「能力 ACE」再放行。

事故就出在这步。在数据盘随手 `mkdir` 一个目录、拿它当工作区跑流水线，会发生什么：

```
Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(D:\proj)
```

`Win32 5 = ERROR_ACCESS_DENIED`，重试无效，错误逐字相同。这个错误只出现在会话深处的工具结果里，模型看到的是「我的命令失败了」——于是它的反应完全符合直觉：重试，再重试，然后开始长篇推理。

## 二、第一层：先让它别烧钱（止损）

当时那个阶段的真实账单（历史数据，宿主 `0.1.7-alpha.1`，下同）：

| 步骤 | 输出 tokens | 内容 |
|---|---|---|
| #1–#9 | 250 / 70 / 106 / 357 / … | 工具调用，其中 6 次是同一句 shell 命令 |
| #10 | 19,172 | 62,668 字符推理 + 2 个 tool call |
| #11 | 32,000（撞输出上限被截断） | 90,266 字符推理，正文仅 172 字符 |
| **阶段合计** | **52,588** | 11 次调用，**零产出** |

排查时最坑的一点：**最先看到的症状是 `max-tokens`**，我们一开始就按「输出上限」排查了很久，方向全错。环境故障换上了一件模型故障的外衣。

第一版修法没有碰 ACL，而是给插件加了一条早停判据：**结构化地看** `tool/result.isError === true`，同一个工具连续以同一错误失败就中止本次尝试，并在结果里点名「环境不可用 + 原文错误」。判据必须用结构化字段而不是猜错误文本——这是这次事故教的第一课。

效果（同一工作区、同一故障）：

| 版本 | 阶段结果 | 输出 tokens | 时长 |
|---|---|---|---|
| 无护栏 | `max-tokens`（误报，真因被掩） | 52,588 | 3 分 45 秒 |
| 加护栏后 | `env-unavailable` + 点名环境与原文错误 | **1,510** | **15 秒** |

52 倍的差距，但请注意：**这只是止损**。用户侧的体验仍然是「流水线第一步停了，我要自己排查 ACL，手动 `icacls` 修复，再 resume」。而且因为是权限问题，每个新建目录都会再来一遍。我们自己的开发流程里，这个「排查几分钟」重复了 N 次之后，终于下决心回答一个问题：**这个能不能根治？**

## 三、根因：一组四态控制变量实验

先交代当时的错误答案。最初的上游报告（已提交给宿主项目）推测根因是「写 SACL 需要 `SeSecurityPrivilege`，普通用户令牌没有」——因为手工 `icacls /setintegritylevel` 确实报 Access denied。**这个结论是错的**，我们后来用控制变量实验推翻了自己。

正确的做法是把沙箱授权要做的每项编辑拆开，逐位补权，看哪一位是成败的分界：

| 实验态 | 结果 |
|---|---|
| 目录 DACL 无任何显式 ACE（数据盘新建目录的默认态） | **失败**（Win32 5） |
| 只补 `WRITE_OWNER` 一个权限位 | **成功** |
| 只补 `WRITE_DAC` | 失败 |
| 补 Full Control | 成功 |

四个态，唯一穿越成败分界的变量是 **`WRITE_OWNER`**。

为什么一个「写文件权限」的沙箱需要的是所有者权限位？拆开宿主沙箱的授权调用看：它在**同一次** `SetNamedSecurityInfoW` 里做三件事——给能力 SID 加写 ACE（DACL）、抑制外部删除（DACL）、**把目录标记为低完整性**（这是写进 SACL 的 mandatory label）。前两件是 DACL 编辑，owner 身份隐式就有 `WRITE_DAC`，够用；第三件写 SACL，需要的正是 `WRITE_OWNER`。

而成败与否，取决于目录 DACL 的继承链里有没有给当前用户的**显式** ACE：

| 位置 | 继承 DACL 里的用户 ACE | 首跑结果 |
|---|---|---|
| 系统盘用户目录（`C:\Users\...`） | 继承链自带 Full Control（含 `WRITE_OWNER`） | 必成 |
| **数据盘新建目录（`E:\...`、`D:\proj`）** | 通常只有 `Authenticated Users:(M)` + `Users:(RX)` | **必败** |
| `%TEMP%` | profile 继承链自带显式 Full Control | 必成 |

这就是「为什么我换个目录就好了」的完整解释：不是玄学，是每棵目录树的继承 DACL 里有没有那一位权限。也解释了为什么 owner 反查总是「目录就是我自己的」——**你是 owner 没用，你要的是 owner 之外显式落在 DACL 里的 `WRITE_OWNER`**；owner 身份隐式授予的只有读控制和改 DACL。

## 四、修复：插件层的启动前自愈（不需要管理员）

根因在宿主的 `grantWrite` 里，但我们没有等宿主发版，而是在插件层做了自愈（宿主侧正解仍在上游跟进）。设计上有三条约束：

**① 时机：在任何模型调用之前。** 流水线起跑的第一件事就是预检——比 PRD 阶段、比所有子代理都早。问题要么被修掉，要么在被烧掉一个 token 之前明确失败。

**② 用宿主自己的 ACL 包、派生同一个工作区 SID。** 沙箱的工作区 SID 是由规范化路径确定性派生的（`S-1-4-x-y` = 路径哈希），预检直接复用宿主包的同一算法物化 standing 授权。这样宿主随后做真授权时会命中它的**幂等快路径**（精确 ACE 已存在就跳过）——零重复、零残留，落盘的 ACE 就是宿主本来要落的那条。

**③ 修复 ACE 只含一个权限位。** 授权拿不到时，补一条修复 ACE。这里有个关键观察：**补 ACE 这个动作本身只是改 DACL，owner 隐式的 `WRITE_DAC` 就够**——所以只补 `WRITE_OWNER` 一个位（`(OI)(CI)(WO)`，可继承），整个修复**不需要管理员权限**。四态实验里「只补 WRITE_OWNER 就成功」正是这条设计的直接依据。

仍失败时（权限面被更严格管控的机器），run 立即失败并附一条可复制的修复命令和「修完 resume 即可」的指引——失败发生在任何子代理之前，而不是跑到开发阶段才炸。

## 五、端到端实测

根因实验当晚，在真实流水线上验证（v0.2.1 发布前的验收 run，数据摘自 run journal，可逐字核对）：

| 项 | 值 |
|---|---|
| 场景 | 数据盘全新目录（此前的必败场景） |
| 预检时机 | run 启动后 **64ms**，首个模型阶段前 ~1 秒 |
| 预检日志 | 「ACL 预检：工作区沙箱写授权原本不可用（目录 DACL 缺 WRITE_OWNER，数据盘上新建目录的常见坑），已自动补写修复 ACE——本次与后续运行均可正常进入沙箱」 |
| 全 run 授权错误数 | **0**（journal 全文无一条 `Win32 5` / `grantWrite`） |
| 流水线 | full 档 11 个阶段（PRD → 技术方案 → 5 个并行开发 → QA → 缺陷修复 → 复验 → 验收）全部完成 |
| 规模 | 198 次模型调用，输入 211,297 / 输出 205,832 token，17 分 41 秒 |

同一天对照的旧版本行为：同一个数据盘新建目录，第一波开发任务双双撞上 `grantWrite (Win32 5)`，第一波失败后门禁拦下后续波次，转人工排查——**两相对照，就是「每次新目录排查几分钟」和「无感知」的差别**。

## 六、复盘：三条可以带走的

**1. 环境故障最贵的不是故障本身，是它的伪装。** `max-tokens` 是表层症状（模型烧到输出上限），真因在环境。如果只看最后一条报错，排查方向从一开始就是错的。给 agent 基础设施做告警时，值得专门问一句：这个失败方式，会不会把人引去查模型？

**2. 判据用结构化字段，定位用控制变量。** 前者是对付「同类错误反复出现」（`isError` 位 vs 猜错误文本），后者是对付「机理不明」（逐位补权定位单一变量）。两件事我们最初都走了弯路：护栏第一版猜文本，根因第一版猜 `SeSecurityPrivilege`——**猜的结论都要能被实验否决，才敢写进文章**。

**3. 「止损」和「根治」是两件事，都做，但别混淆。** 早停护栏把 52,588 降到 1,510，值得做；但它不消除问题，只是让问题便宜。真正的根治是「让问题不再发生」（预检自愈），而它的设计依据——「修复只需 owner 隐式权限」——恰恰来自根因实验。止损买时间，根因实验买正确的设计。
