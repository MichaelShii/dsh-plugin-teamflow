# ADR-0010：澄清的可观测性与失效路径（先埋点，再谈策略）

- 状态：**已接受（Accepted）**——顺序与方向已定；具体参数列为「待定」，实现前需逐条确认
- 日期：2026-09-30
- 关联：issue [#11](https://github.com/MichaelShii/dsh-plugin-teamflow/issues/11)（fine-grained multi-dimensional discovery）、ADR-0004（分诊与共享状态）、ADR-0005（拒绝无效需求）、`host/index.ts`（`clarificationPreflight`）、`host/core/pipeline.ts`（`abortForClarification` / 收敛规则）、`host/core/triage.ts`（`qualifyBlockers` / `fallbackVerdict`）、`docs/TODO.md`「需求澄清 / 计划确认闸门」

## 背景

issue #11 提议把启动前澄清从「一次泛问」升级为**多维度、多轮、带到 ~95% 置信度为止**的访谈（原型是 `interview-me` skill：一次一问、每问附带一个猜测、最后回写一份含 Out of scope 的确认单）。

评估过程中出现了一次**统计纠错**，它比 issue 本身更值得记录：

- 初版统计（85 个 run）得出「澄清闸门从未触发过」——`journal.triage.blockers` 分布为 `{0: 28}`、`blockersDropped` 全 0、`intent` 全为 `requirement`。
- 用户据自身记忆提出质疑（「我写贪吃蛇的那几个需求的时候，有主动提问架构和展示方式的一些选型」）。
- 复核后**用户是对的**：真实澄清至少发生过 4 次，内容正是技术栈与运行形态选型。

结论：**`journal.triage.blockers` 在结构上永远看不到澄清**，用它做统计必然得出「从未触发」的反结论。

## 核实的事实（2026-09-30，只读统计 85 个已落盘 run）

### 1. 为什么 `blockers` 恒为 0——设计使然，不是没发生

澄清命中时 `teamflow_start` 返回 `needs-clarification` 且**不建 run**；`journal.triage` 只在**建了 run 之后**落盘。因此：

| 时点 | 是否建 run | 裁决是否落盘 |
|---|---|---|
| 澄清前（提出问题时） | **否** | **否**——最有信息量的那一次不落盘 |
| 澄清后（用户答完重调） | 是 | 是——但此时 blockers 已被收敛规则放过（=0） |

⇒ `blockers` 恒为 0 是**结构性盲区**，与「闸门有没有工作」无关。

### 2. 真实发生过的澄清（`journal.requirementSupplement` 非空，4 例 / 85）

| run | 长度 | 内容 |
|---|---|---|
| `tf-mul7m3ed-pzangy` | 268 | 贪吃蛇：**运行形态**（网页版）/ **技术栈**（原生 HTML+CSS+JS、无构建）/ **玩法范围**（基础版最小闭环） |
| `tf-mul4t5ga-ajs4i4` | 46 | 贪吃蛇：技术栈选择（纯 HTML/CSS/JS，无构建工具） |
| `tf-mulkl368-ag6u1m` | 302 | 缺陷返工方式裁定（返工后再验收 vs 直接合回） |
| `tf-mu4i779p-kze5kl` | 2095 | 插件安装形态（profile 层声明与打包缺口） |

**即：闸门在真实场景里是有效的，且集中在「说不清的需求」上**——这正是它被设计出来要拦的那一类。

### 3. 分诊 fallback 时闸门静默失效（4 / 28 个有 triage 记录的 run）

`fallbackVerdict` 硬编码 `intent: 'requirement'` + `blockers: []`，注释原话「兜底路径**永不拦启动**」。后果：

| run | 需求 | 结果 |
|---|---|---|
| `tf-mu4bve7t-duux2k` | 「我想开发一个 dsh 插件」 | fallback → medium → **直接跑完** |
| `tf-mu5eyi4d-0jbfk8` | 开发 Standup Reminder 插件 | fallback → full |
| `tf-mu5t4zml-4wbmbz` | 给提醒横幅加一个按钮 | fallback → medium |

第一条正是社区讨论 [#6405](https://github.com/deepseek-ai/deepseek-harness/discussions/6405) 记录的案例（「我都不知道自己想要啥」）。**闸门在最该拦的那一例上，因为分诊超时退兜底而完全失效，且用户侧不可见。**

### 4. 档位与成本台阶（供策略设计参考）

| 档位 | n | stages 中位 | 时长中位 | 调用中位 |
|---|---|---|---|---|
| patch | 19 | 2 | **2 min** | 25 |
| lite | 31 | 7 | 26 min | 139 |
| medium | 26 | 10 | 50 min | 193 |
| full | 7 | 9 | 25 min | 175 |

「简单修改不走完整流水线」不是待议项——`patch` 档（单 agent 直改 + 记账）已承担 22% 的 run，且 `patch` 本就豁免分诊。

## 决策

### D1 顺序：可观测性 → 失效路径 → 策略扩展

三步按此顺序推进，**前两步未完成前不实现 `interview` 档**：

1. **补澄清埋点**（shadow，先行）；
2. **修分诊 fallback 时的闸门静默失效**；
3. **再定澄清强度策略**（含 `interview` 档）。

理由：`interview` 的效果无法在现有埋点下验收——做了也测不出来。

### D2 埋点必须落在「建 run 之前」，且不得只记成功样本

澄清发生在 journal 存在之前，因此埋点需落在**产品线目录**级的事件流（落点见「待定」）。**不得采用「只在澄清后建 run 时把记录整体带进 journal」的方案**：那只能观察到「澄清成功」的样本，看不到「问了但用户没答」「反复问直到用户放弃」——与本次纠错犯的是同型错误（用幸存者样本下结论）。

### D3 澄清强度是 `MODE_REGISTRY` 的一个策略维度，不是一条独立路线

`MODE_REGISTRY` 本就是策略表（每档声明阶段集 / PRD 形态 / 独立 QA / 技术文档）。澄清强度作为其新维度，取值语义为 `off`（patch 现状）/ `once`（现行默认）/ `interview`（显式开）。**`patch` 档恒为 `off`，不受本维度影响。**

### D4 `interview` 若实现，必须带硬终止

不得只以「置信度达标」为停止条件（原型 skill 的停止测试是「能否预测用户对下三个问题的反应」，非轮数）。硬终止至少三条并存：轮数上限、置信度不再上升即停、用户可随时「够了」。依据：同一闸门的早期版本因反复追问造成 **6 轮零 run**（见 `docs/TODO.md`）。

### D5 约束：访谈只能发生在主会话

流水线阶段均为子代理，而子代理**不能向用户提问**（宿主 `DELEGATED_CALLER` 拒绝，ADR-0005 已记录）。因此 issue #11 的实现选项 A（新增前置阶段 `discovery`）**不成立**——无论澄清强度取何值。

## 待定（实现前逐条确认）

| # | 待定项 | 候选方案 |
|---|---|---|
| 1 | 埋点落点 | ① 产品线目录 `clarify/<key>.jsonl` 事件流（append-only，建 run 后关联 runId）；② 事件流 + 建 run 时快照进 journal |
| 2 | 埋点字段 | 轮次序 / blocker 指纹（`settles` + question） / 条数 / 答复长度 / 澄清前后 `mode`·`intent` 是否变化 / 用户是否答复 |
| 3 | fallback 时的闸门行为 | ① 保留放行但**让用户可见**（汇报明写「未能确认需求意图，已按假设启动」）；② 降级为**确定性形态判据**兜底拦一次（如短需求 + 无验收判据 + 无交付形态）；③ 与 ① 叠加 |
| 4 | `interview` 档默认矩阵 | 各档位默认值、能否按显式参数开启、轮数上限取值 |
| 5 | 去交互化机制的取舍 | `restate` 六行（含 Out of scope）/ 维度完备性自查 / `confidence` 信号——哪些并入 PRD 与汇报（**不依赖 D1~D4，可独立评估**） |

## 影响

- `docs/TODO.md` 的「需求澄清 / 计划确认闸门」条需按本 ADR 重组：其 Phase 2（PRD 确认单）与本 ADR 的 D3/D4 是同一件事的两个侧面，不应各做一套。
- issue #11 的回应：接受其**问题陈述**（假设静默变成 spec），不接受其**实现选项 A**（D5）；`interview` 作为策略档（D3）而非新阶段。
- 明确一项**已知观测缺陷**：现有 `journal.triage` 无法反映澄清行为，任何基于它的统计都不可用于判断闸门有效性。
- D1 的第 1、2 步为 policy/观测级改动，不改状态机；第 3 步涉及跨调用状态，改动面较大。

## 再评估的触发信号

1. 埋点攒到足量样本后，出现「澄清命中率高但答复未改变范围」（说明在空问）或「命中率极低但返工与需求偏差有关」（说明漏问）；
2. 出现真实的多轮诉求实例（用户明确要求继续追问，或一次答复后仍有显式未决项）；
3. 外部任务平台对接立项（需求不再只来自对话窗口，澄清的触发与形态需重新评估）。
