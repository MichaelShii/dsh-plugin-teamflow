# ADR-0005：需求无效 → 验收阶段「需求不适用」拦截（不误标 accepted）

- 状态：已接受（Accepted）
- 日期：2026-08（v0.1.0）
- 关联：`host/core/pipeline.ts`（验收段 accVerdict）、`host/prompts/index.ts`（acceptancePrompt）、`host/core/backlog.ts`

## 背景

端到端复验「需求与实际不符」场景（如要求删除一个不存在的字符）时暴露：
- **dev 执行纪律生效**：确认单与开发正确指出「需求与现状不符 / 无需改动」，未臆造改动（此前问题已修）。
- 但**验收 agent 把「无缺陷 + 无需改动」判成了「✅ 通过」**，需求被误标 accepted。

根因：`acceptancePrompt` 的验收结论只有三档（通过/有条件通过/不通过），缺少"需求本身无效"的语义出口；对「无变更的正确拒绝」模型倾向视为通过。

## 决策

1. **验收结论新增第四档「📝 需求不适用」**（`acceptancePrompt`）：当 PRD/变更单/确认单已指出"需求与现状不符"，或开发明确"无需改动（需求站不住/已满足）"时，结论应为「📝 需求不适用」，不得因无缺陷标 ✅ 通过。
2. **executePipeline 验收段拦截**：验收文本命中 `需求不适用|需求与实际不符|需求站不住|无需改动|无需修改|需求无效` → `accVerdict = 'reject'`：
   - acceptance task → `needs-human`
   - req → `needs-human`（humanIntervention=true，需人工决定调整或取消需求）
   - 流水线中断（throw，journal.status=failed）
   - 原 `❌/不通过/需返工 → rework` 路径保留（针对交付未达标的场景）
3. 需求有效性**前置拦截**（在 PRD/确认单阶段就判别并停）是更彻底的方向，暂不实现（见「触发信号」）。

## 理由

- 「需求无效」与「交付不达标」是两类不同终止：后者可返工（rework），前者应停流水线交人工裁夺（needs-human），混为 accepted 会掩盖需求本身的问题。
- 在验收提示中显式给出该档，模型才有正确归类的词汇；正则捕获让判定确定性可测。

## 影响

- 需求无效 → req/acceptance 卡 `needs-human` + 人工介入横幅出现，团队台明确提示。
- 端到端可用「空需求/需求站不住」场景验证红路径。

## 触发信号 / 后续

- 需求有效性前置到 PRD/确认单阶段（一发现不符即停，省去开发与验收整段）：可作为 v0.1.0 增强。
- full/medium 档位阶段集差异化执行仍待做（ADR-0004 §影响）。
