# 锚点详情：中断运行（cancel，2026-09-16）

> 本文件是 `AGENTS.md` §5 中「中断运行（cancel，2026-09-16）」锚点的**论证、实锤与门禁细节**——从 AGENTS.md 原文迁出，
> 内容逐字保留（仅把表格分隔还原为正常 Markdown 段落）。**行为不变量以 `AGENTS.md` §5 为准**；
> 本文件属可检索层，**不注入会话**（同 `docs/devlog.md` 的定位）。

界面可直接中断在跑的流水线：**三处入口**（会话内工作台顶栏「⏹ 中断 #xxxxxx」/ 全局面板 run 行 / 右栏与浮层的 run 详情头），共用 `client/shared.tsx` 的 **`CancelButton`（两段式内联确认**：首次点击进入待确认态、3 秒内再点才执行——客户端无宿主 confirm/dialog 依赖，不引新依赖；面板行整行可点开详情，按钮自己 `stopPropagation`）。数据面 = 既有 `teamflow/cancel`（descriptor 参数**恰为 `[runId]`**，客户端经 `productApi.cancel` / `api.cancel` 调同一条）+ dispose **DSH 原生 `SubagentRun.dispose()`**（官方契约「cancel remaining work, reach child quiescence」，宿主另有 `subagents/interruptByParent` 只服务 continuable 常驻子代理，流水线是一次性 run **不得走它**）。**`cancelRun` 的 `status !== 'running'` 门禁是硬要求**：非 running（completed/failed/interrupted/pending/未知 id）一律 false——旧实现对任意内存内 run 都置 cancelled 并返回 true，会污染已完成 journal，且对重启后回填的 interrupted run 是「提示成功、状态永不变」；取消失败必须可见（工作台报 `cancel.failed`、面板给 hint）。**只置位不改状态机**：终态由 executePipeline 收尾落定（`cancelled` + **不提交** + 保留 resume 入口）；**阶段间隙（`inFlight` 为空）也必须可取消**（host 侧 IO 期间按钮不能失效）。**并发多路一次全停 + 取消后不再取新任务（2026-09-16 实测修正，勿回退）**：① `inFlight` 形状 = `runId → Map<stage, run>`（`trackInFlight`/`untrackInFlight`，runner 阶段末只注销自己那一路），`cancelRun` **遍历 dispose 全部**在飞子代理——旧形状（每 run 一个 handle，后启动覆盖前一个）只停最后一路，用户实测「开发的多 agent 中断不了」；`dispose()` 的 Promise 一律挂 `.catch`（拒绝不得变成未处理拒绝）。② 并发池 `util.runPool(items, max, fn, shouldStop?)`：**取下一个任务前判 `shouldStop`**，dev 与 resume 补跑两处传 `() => journal.cancelled`——旧实现 worker 拿到被取消任务的 null 结果后立刻 `cursor++` 取下一个任务并起新子代理，用户实测「中断了又自动启动一个」（取消变成队列补位）；未启动条目结果为 `undefined`，调用方必须按 `r &&` 过滤。**`cancelRun` 住在 `core/context.ts` 而非 pipeline.ts**：pipeline 链到 `report→@deepseek-ai/dsh-llm`（宿主私有 peer，仓库内无 node_modules）→ 行为级测试取不到；放 context 后 `test/cancel.test.js` 可真跑（门禁/置位/dispose/落盘/阶段间隙/dispose 抛错 6 组 + descriptor↔服务↔三处 UI 入口同源断言）。中断后界面靠既有轮询刷新（工作台 2s / 面板 8s），不新增事件通道。**阶段状态词表与 backlog 词表分道**（2026-09-16 实测截图修正）：`status.*` 是 backlog 卡片词表（`closed`/`cancelled`/`verified` 都译「已关闭」），阶段渲染必须走 `shared.stageStatusText`（`cancelled` → `stageStatus.cancelled`「已中止 / Stopped」），**禁止回退 `stText`**——否则被中断的阶段显示「已关闭」（en `Closed`），与同屏 run 行的「已取消」自相矛盾（smoke 有闸 + 词条 zh/en 同形门禁）。**dev 收口的「取消检查 + 提测门禁」必须落在 `if (resume) / else` 两分支的汇合点**（2026-09-16 实测：resume 后中断，dev 三路全「已中止」却径直起了 QA 子代理——这两个判断原先只写在「新开发」分支里）：顺序还必须**先取消检查、后提测门禁**（取消时任务的 failed 只是「没跑完」，不该被记成提测失败转人工），且提测门禁因此同样覆盖 resume 补跑失败（对齐 r26「任务 failed 不进 QA」语义）；smoke 两条源码断言守门（汇合点顺序 + 门禁只有一处）。**终态归一必须放在 finally 首句**（2026-09-16 实测，勿删）：取消若走 `if (journal.cancelled) return` 这条**正常返回**路径，唯一落 `status='cancelled'` 的 catch 块不会执行 → run 卡在 `status='running'` 且 `cancelled=true`：① 工作台永远「运行中」+ 中断按钮（再按取消也无效——门禁只认 running、恰好放行，但已无在飞子代理可停），同时给出「↻ 从断点重跑」→ 点一次重跑一轮 dev → 再取消，**死循环**（实测 01:59 / 02:03 两轮）；② 完成汇报按 running 渲染，出现「状态：running」却 cancelled=true 的自相矛盾（主线程据此怀疑 host 在自动续跑）；③ 归档与孤儿收口（`journal.status === 'cancelled'` 分支）全被跳过。故 `if (journal.cancelled && journal.status === 'running') → cancelled` 落在 finally 首句（幂等；completed 不受影响），smoke 两条断言守门。**取消来源必须落盘、取消态不得给模型续跑引导**（2026-09-16 实测补充）：取消来源分三类——界面按钮=`ui`（人工）、模型工具=`tool`、历史/未知=`unknown`，落 `journal.cancelSource`/`cancelRequestedAt` + journal.logs 记一条「收到中断请求（来源：…）」，并在完成汇报里显式给出「中断来源：{source}」（主线程曾因无来源信息+状态矛盾而误判「另一会话在自动续跑」）；**取消态的 `report.nextCancelled` 取代 `report.next`**——明写「本 run 不会自动续跑（host 无该机制），要续跑请让用户点工作台『↻ 从断点重跑』，不要自行调用 teamflow_resume」（旧文案 `report.next` 直接把 teamflow_resume 当"下一步"教给模型，等于邀请它替人做续跑决定）
