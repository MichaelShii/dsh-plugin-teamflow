**形态是需求的维度**（非关键词）。链路：`triage` 判 `artifact`(app/plugin-host/plugin-client/plugin-full/cli/lib/docs/data/other)+`installable`+`host` → 数据表 `ARTIFACT_CONTRACTS` 展开（**新形态只加一行数据**）→ `pipeline` 注入 `__runCtx.artifactContracts` → `prdPrompt` **强制写成可测 AC**（`other`/`app` 不注入）。
**① 不硬编码宿主字段名，样本也不写死**：只写"要求+判据形态"，字段名必须核实。样本**首选** `LOCAL_PLUGIN_SAMPLES_HINT`=`$DSH_HOME/profiles/*/node_modules/<任一 dsh 插件>/`（任何开发机必有；其 `package.json` 的 `dsh` 块与 `cordis.patch.yml` 是权威现场）；本仓 `ARTIFACT_REFERENCE_SAMPLES` **降为次选**——实测 `npm pack` 只发 10 文件、**源码根本不发**，用户机器上该路径不存在，只指它 → 退化成空话。
**② 安装入口同样不写死，且主源是宿主权威锚点、不是环境变量（2026-09-21 用户实锤纠正）**：`dsh plugin --profile web add` 在**源码运行**（`pnpm dsh`，dsh 不在 PATH）或 profile 名非 web 时直接失效。故 `util.detectInstallEnv` 起跑**运行时探测**，取值顺序 = **① `ctx.baseUrl`（= 当前 profile 目录；宿主在挂载插件树前设好，Cordis 子 ctx 原型继承；经 `context.installCtx` 从 `TeamflowService` 构造处搬运给 pipeline，pipeline 无 ctx 且链宿主私有 peer，不得反向依赖）② 插件自身路径反推（`link:`/junction 下 `import.meta.url` 解析到真实目标 → 必落空，仅次源）③ `dshHome()` 只补 home**；`ok = !!profile && isAbsolutePath(profileDir)`（相对目录照做不了，不算成功）。**为什么不得用 `DSH_HOME`**：它**不是"装了 dsh 就自带"**——是可选覆盖变量（`home-paths` 优先级「显式配置 > `$DSH_HOME` > `~/.dsh`」），装 dsh 不写它（本机 User/Machine 作用域实测均空），`.env` 永久设不了（`app-boot` 的 `BOOTSTRAP_PREFIXES` 含 `DSH_`，命中即抛），宿主进程里通常 `undefined` → 纳入 `ok` 会让**默认安装的用户被误判成"探测失败"**并降级为"问用户"（旧实现正是如此：`profileFromModulePath` 已算出 `home`/`dir` 却只取 `.profile` 再重拼）。**特别注意**：`shellEnv` 每次 shell 调用**现算**一个 overlay（官方契约「discards inherited `DSH_*` … `process.env` is never modified」），故 `pwsh`/`bash` 里 echo 得到它**与宿主 `process.env` 无关**——不要用 shell 观测推断宿主环境（本轮因此误判过一次）。双注入（`__runCtx.installEnv`/`journal.installEnv`），汇报给「🧩 安装待办」。**探测失败(`ok=false`) → 改为"问用户"，绝不编路径**。**存储面不受影响**：`store.dshHome()` = `process.env.DSH_HOME
