# 锚点详情：发布与分支流程（AGENTS.md §4「发布」条目原文）

> 从 AGENTS.md §4 迁出的完整发布/分支流程（发版 SOP、分支模型沿革、判定发布是否成功的判据）。
> 迁出后 AGENTS.md §4 只留不变量 + 指针；内容逐字保留。

`npm publish`（升 `package.json` version 后；`files` 白名单 = `lib`/`cordis.patch.yml`/`README.md`/`README.en.md`/`CHANGELOG.md`，`prepublishOnly` 自动 bundle+全套测试；包名无 scope 默认公开，registry 为 npmjs.org）。**发版 SOP**（2FA 人工节点、release note 必须由 `git log <上一tag>..HEAD` 生成而非凭记忆、已知坑清单）见 skill `release-npm-package`。**分支模型（2026-09-16 起，勿回退）**：`main` = **线上发布版本**——只承载「已经发布到 npm 的内容」，与 npm `latest` 保持一致，**不承接日常提交**（含文档/流程改动）；日常开发与文档改动一律落在**当前 release 分支** `release-vX.Y.Z`（每个发布周期一条、长期存在并推送远端，CI 也按 `release-*` 触发）；**贡献者向最新 release 分支提 PR**（见 `CONTRIBUTING.md` §PR workflow），不向 main 提。发布时：release 分支 → PR → **合入 main（保留全部提交的真实合并，`gh pr merge --merge`；不用 squash，也不用 rebase）**（这一步是 main 唯一的入口）→ 打 tag → 发 GitHub Release → 删掉该 release 分支并另起下一条。**为什么不用 squash（2026-09-23 维护者拍板）**：release 分支发布后会被删除，squash 会把整条开发过程压成一个提交，**main 上再也看不到过程**；保留提交的代价只是 main 的历史带合并点，可接受。**定稿顺序**：版本号 + CHANGELOG 日期 + `docs/releases/<v>.md` 一起定稿 → `npm publish`（人工节点）→ `git tag -a v<v>` 打在 main 的发布提交上并推送 → `gh release create --notes-file docs/releases/<v>.md`。**判定发布是否成功看写路径**：registry 读路径（`npm view` / packument / `/<pkg>/<v>`）可滞后数分钟，据此误判「没发成功」会导致重复引导发布；重发得到 403 `cannot publish over the previously published versions` 才是权威回执（幂等安全，无副作用）。历史沿革：v0.1.5–v0.1.7 与 v0.1.9 为本地 squash 直推 main，v0.1.8 试过一次 PR，本模型自 **v0.2.0**（分支 `release-v0.2.0`）起固定；**合入方式自 v0.2.0 起改为保留提交的真实合并**（v0.1.x 全程用 squash）。
